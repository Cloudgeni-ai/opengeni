A managed browser's tabs now keep their IDs when the browser is relaunched, and a call naming a tab that no longer exists says why it is gone and how to carry on, instead of only "browser target does not exist". Tab IDs used to be the browser's own target IDs, which change whenever its process is relaunched. When browserd stops a managed browser (after it goes unused for the idle release time, or when its controller restarts), it keeps the browser's tabs in the session directory, as a hash of each page's URL. The next launch on that profile, and the relaunch after a lost browser process or a state capture, matches them to the tabs it reopened, and each reopened tab keeps its earlier ID. A tab is matched only when it is the one tab showing its URL before and after, so tabs that share a URL never take each other's IDs. A controller that reattaches to a running browser after a restart gives its tabs the same IDs. An old tab ID that no reopened tab took over answers that the browser was stopped and relaunched, that this tab was replaced, that its page may be open under a new ID and unsaved page input may be lost, and to list the current tabs. A tab the driver saw close says when, and whether a close-tab call or its page or someone using the browser closed it. Any other unknown ID says to list the current tabs and use one of their IDs. Every message still starts with "browser target does not exist". An action refused before dispatch because its tab is gone now keeps the driver's target_not_found code and explanation instead of a generic driver failure.
