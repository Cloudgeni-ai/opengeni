Windows computer use can set the text of Notepad's document and of other classic Edit and RichEdit text fields with `set_value`. In some apps (by program name, Notepad among them) CUA disables the app's window while it sets a value, so that the app cannot take the foreground, and a classic Edit control then refuses the write. CUA reported this as "does not implement ValuePattern", and the action came back as an unknown outcome, so the agent had to type instead. When CUA refuses that way, browserd now selects the field's whole text and replaces it through the field's own control, as typing would (the app sees the change and it can be undone), without bringing the window forward, then checks that the field reads the value. The control written is the one visible Edit or RichEdit control whose window rectangle is exactly the element's bounds; when there is none or more than one, or when another settable element of the window has the very same bounds (a text box filling a container that is itself shown as a text field), nothing is written, so a text box nested inside the element, around it or filling it is never written instead. A password field, whose text another process cannot read, is never reported as reading the value: when the control marks its text edited by the replacement, its length matches, and the value has no letters the field changes (a field that turns letters into capitals or small letters), the action completes as unconfirmed input, so the agent is told to check the window when nothing visibly changed; otherwise it gets a definite failure. A read-only or disabled field gets a plain refusal with nothing changed, and an element that is not such a field gets a definite refusal that says to click into it and type instead. A window's title bar no longer offers `set_value`, since its value is its title and cannot be set.
