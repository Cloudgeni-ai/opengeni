The compute leader now shrinks its host group by itself. After its group has had more spare than it needs for 30 minutes (`--scale-shrink-after-s`, 0 turns it off), it drains the live host with the most memory free without ending any VM process (then the one holding the fewest sandboxes), sleeping each idle sandbox there with its programs before moving it, and removes the instance through the group's `deleteInstances` once the host owns nothing and has drained for 15 minutes since its first drain pass that held. It never goes below `--scale-min`, removes one host at a time, waits as long again after any grow or removal, and takes the host back if the group would grow or the drain has not finished within six hours (`--scale-drain-within-s`; that host is then left alone for as long), never once its removal was asked for. A draining host is given no sandbox it does not own already. The store notes the leader's drain and when it began (compute schema version 12, two nullable columns), so a new leader after a deploy goes on with it. A host an operator drains is never removed unless `--scale-adopt-drained-after-s` is set (default 0, off). New `compute_fleet_shrink_*` metrics report the host on its way out, its drain age, sandboxes left, removals, take-backs and skipped hosts. Connected Machines are not part of any host group and are never touched.

Shrinking is on wherever a host group is configured (`--gcp-group`; staging today, production runs on Modal), but only while every live host of the group reports `keeps_memory`. Upgrade order: hosts first, then the control service. Until every host runs this release, the leader does not shrink and reports `compute_fleet_shrink_held_back 1`.

A host hand-off can now ask to keep the sandbox's memory (`keep_memory`): the host then saves an idle sandbox with its programs, deciding by how it is when the hand-off arrives. Hosts say they do (`keeps_memory` in their description).
