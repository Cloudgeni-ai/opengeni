Attached Chrome sessions now survive a restart of the extension's background worker. Chrome stops and restarts an extension's worker whenever it likes while it keeps the tabs and the extension's debugger attachments, but the extension used to start a new state generation with every worker, so each such restart ended every browser session on the profile. The extension now keeps its state generation and the tabs it has attached in `chrome.storage.session`, which Chrome keeps exactly as long as those attachments. A new worker checks each recorded attachment with a debugger command that changes nothing, carries on with the ones that answer, and reconnects under the same generation, so the same browser session continues on the same tabs. An attachment an earlier worker left without recording it is taken over instead of refused. Reloading or updating the extension, or restarting Chrome, still starts a new generation and ends the sessions as before. Each time a worker carries on an earlier worker's state, the extension records how many attachments it kept, how many had ended and how many tabs were closed (`stateResumptions` in the extension's local storage, the latest 20).

A command that was in flight when the worker stopped still reports its outcome as unknown, and nothing replays it. Each event poll now names the worker's event stream; browserd treats a new stream as lost event history and resynchronizes even when the new worker's sequence numbers have caught up with its cursor, and a tab whose input was in flight on the old worker can be used again once a new worker answers. Ending or leaving an attached session also no longer closes an empty tab that is still on its way to a page.
