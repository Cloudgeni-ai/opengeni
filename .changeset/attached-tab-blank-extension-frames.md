Attached Chrome keeps working on sign-in pages whose password manager loads its inline menu into a frame it created blank. The extension found other extensions' frames only by their address, and such a frame's address stays blank while it shows the other extension's page, so Chrome kept refusing the tab and every call failed with "it could not be removed". The extension now also removes such a frame when Chrome's own reports single it out: Chrome lists every other frame of its page to the extension, each of those ran the extension's script and said so, and Chrome's debugging targets hold another extension's page. A frame that merely does not answer is never removed, so a page's own frames (including error pages, frames still loading or posting, and sites the person took the extension's access from) always stay; when the page holds one of those, the menu frame is not removed either, and the tab can be debugged again once the menu closes. This adds the `webNavigation` permission, which brings no new permission warning. A removal that removes nothing no longer counts towards the tab's removal limit, so it is no longer reported as an extension that keeps adding its frame.

An observation made just before Chrome ended the tab's debugging (as it does whenever another extension adds a frame) now still holds when the new attachment finds the same document. browserd used to give every new attachment a new target, document and frame generation, so an action right after a fresh observation failed with `target_stale` whenever a password manager's menu appeared in between. A new attachment now keeps the ended one's generations and element references when the tab's main frame still has the same frame and loader ids; a new document, a crash or a closed tab still gets fresh ones, and commands of the ended attachment still never reach the new one.
