Start agents on a schedule or from your product's events, let them work to completion, and bring the results back.

## On a schedule

```ts
await og.createScheduledTask(workspaceId, {
  name: "Daily ticket triage",
  schedule: { type: "calendar", hour: 8, minute: 0, timeZone: "Europe/Oslo" },
  runMode: "new_session_per_run",
  agentConfig: {
    prompt: "Triage new support tickets and tag urgent ones.",
    agent: { capabilities: { from: "none", knowledge: true } }, // frozen with the schedule
    tools: [{ kind: "mcp", id: acmeServerId }],
    sandboxBackend: "none",
  },
});
```

`agent` is optional; without it, runs use the workspace defaults ([Configure the agent](/integrate/configure-the-agent)). `runMode` picks a new session per run, one reusable session, or an existing session. Select tools by id from a workspace [OpenAPI Integration or MCP connection](/integrate/your-data#openapi-integration).

Manage tasks with `listScheduledTasks`, `updateScheduledTask`, `pauseScheduledTask`, `resumeScheduledTask`, `triggerScheduledTask`, and `deleteScheduledTask`.

To continue an existing conversation, schedule a message for that session:

```ts
const task = await og.createScheduledTask(workspaceId, {
  name: "Daily follow-up",
  schedule: { type: "calendar", hour: 9, minute: 0, timeZone: "Europe/Oslo" },
  targetSessionId: session.id,
  prompt: "Review new tickets and report any that need attention.",
});

await og.updateScheduledTask(workspaceId, task.id, {
  prompt: "Review urgent tickets and report any that need attention.",
  expectedExecutionDigest: task.executionDigest,
});
```

Each run uses that chat's own model and tools and runs as the schedule owner. Updates keep fields you omit; `expectedExecutionDigest` rejects a conflicting edit. If moving `targetSessionId` would change the run's settings, the API returns a conflict; repeat with `adoptSessionSettings: true` to accept.

`overlapPolicy` decides what a run into a chat does when the chat is still busy:

- `steer` (the default): if the busy turn is this task's own earlier run, the new run reaches it at its next model step, like a person's Steer. The tool calls of that step finish, and the agent then reads the new run together with the work so far, so a burst of events is handled as one conversation instead of a queue of separate replies. A turn anyone else started still finishes first, and the run follows it.
- `buffer_one` (`allow_concurrent` is the same in a chat): the run waits and starts when the current turn finishes.
- `skip`: the run is dropped, and the next one runs as normal.

Runs in a new chat (`new_session_per_run`) never wait, so the choice only matters for tasks that continue a chat.

## From your product's events

A scheduled task can also run when something happens: give it `events`, and each event that matches one of its triggers starts a run. Events come from an **event source**:

| Source                                           | Events come from                                                                                                                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{ kind: "mcp", serverId }`                      | An MCP connection whose server offers [MCP Events](https://modelcontextprotocol.io). Opengeni subscribes while an automation listens.                                                         |
| `{ kind: "webhook", adapter: "standard" }`       | Your backend, signed with [Standard Webhooks](https://www.standardwebhooks.com). Opengeni generates the secret.                                                                               |
| `{ kind: "webhook", adapter: "custom", format }` | Any other app's webhooks, read as `format` describes: how they are signed, where the event type is, and whether one delivery holds several events. Linear, Sentry and Tailscale have presets. |
| `{ kind: "github" }`, `{ kind: "slack" }`        | The deployment's GitHub App or Slack bot, set up automatically.                                                                                                                               |
| `{ kind: "gmail" }`                              | A person's Gmail connection, read while an automation listens.                                                                                                                                |

Event triggers are on when `clientConfig.eventTriggers.enabled` is true (`OPENGENI_EVENT_TRIGGERS_ENABLED` on the deployment).

```ts
const { source, signingSecret } = await og.createEventSource(workspaceId, {
  kind: "webhook",
  adapter: "standard",
  name: "Acme",
  visibility: "workspace",
});
// signingSecret is shown once: store it with your backend, which posts events to source.webhookUrl.

await og.createScheduledTask(workspaceId, {
  name: "Triage urgent tickets",
  schedule: { type: "manual" }, // events only; a calendar schedule also works
  runMode: "new_session_per_run",
  agentConfig: { prompt: "Triage the ticket from the event and tag its owner." },
  events: {
    triggers: [
      {
        sourceId: source.id,
        eventTypes: ["ticket.created"], // or "ticket.*"
        conditions: [{ field: "data.priority", op: "in", value: ["high", "urgent"] }],
      },
    ],
  },
});
```

Your backend sends `{ "type": "ticket.created", "timestamp": "…", "data": { … } }` with the `webhook-id`, `webhook-timestamp` and `webhook-signature` headers; any Standard Webhooks library signs it. Each run gets the events that started it. Redelivered events (same `webhook-id`) are ignored, and the agent treats event data as untrusted input.

An app with its own webhook format needs no code: describe the format on a `custom` source and paste the app's secret. `signature.scheme` is one of:

- `standard_webhooks`.
- `hmac_sha256`: the body's HMAC in a header, hex or base64, after an optional prefix. Add `signedContent`, such as `"v0:{header:X-Request-Timestamp}:{body}"`, when the app signs more than the body.
- `timestamped_hmac_sha256`: `t=<unix seconds>,v1=<hex>` over `"<t>.<body>"`.
- `token`: a shared secret in a header.
- `ed25519`: the app's signature, checked with its public key as the secret. It also takes `signedContent`.
- `url_token`: for apps that can't sign. The secret goes in the address as `?token=<secret>`, and it must be at least 24 letters, digits, `-`, `_`, `.` or `~`.

The other fields are dot paths into each event, or headers. `summary`, `subject`, `url`, `actor`, `eventId` and `occurredAt` also take a list of paths, where the first with text wins. `type` and `eventId` can join `parts`: an alert's `status`, `fingerprint` and `startsAt` name one firing episode, so an alert sent again runs automations once, and an event missing a part has no id. `freshness` refuses old deliveries, and `actorKind` says which actors are people. Linear, Sentry and Tailscale have presets that Automations and agents offer by name. Agents add webhook sources with the `event_sources_create_webhook` tool. Tailscale, spelled out:

```ts
const { source } = await og.createEventSource(workspaceId, {
  kind: "webhook",
  adapter: "custom",
  name: "Tailnet",
  format: {
    preset: "tailscale",
    signature: { scheme: "timestamped_hmac_sha256", header: "Tailscale-Webhook-Signature" },
    batch: {}, // the body is a JSON list of events
    type: { path: "type" },
    occurredAt: "timestamp",
    summary: "message",
    subject: "data.deviceName",
    url: "data.url",
    actor: "data.actor",
  },
});
// Paste source.webhookUrl into the app, then its secret:
await og.updateEventSource(workspaceId, source.id, { signingSecret: tailscaleWebhookSecret });
```

- `events.once: true` finishes the task after its first run, for "tell me when this happens". A once-task that continues a chat belongs to it: archiving that chat with Pause removes the task if it has not run yet.
- `events.maxRunsPerHour` (default 30) holds back a burst; held events are batched into the next run, and the owner is told once.
- Events made by Opengeni's own bots don't fire a trigger unless it sets `includeOwnEvents: true`.
- `listEventDeliveries`, `replayEventDelivery` and `sendTestEvent` show what arrived, process a delivery again, and send a test event. `listEventSourceTypes` lists the event types a trigger can name.

### Events from your own MCP server

If your product already gives the agent an MCP server, that server can publish events too, and nothing has to sign webhooks. Opengeni implements the client side of the MCP Events extension ([SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415), `io.modelcontextprotocol/events`):

- Advertise the extension in `initialize` and answer `events/list` with each event type's `name`, `description`, `delivery` modes, `inputSchema` (the subscription arguments) and `payloadSchema`.
- Offer `poll` (`events/poll`), `webhook` (`events/subscribe` and `events/unsubscribe`), or both. Opengeni prefers a webhook, refreshes it before its TTL runs out, and polls instead when your server can't reach Opengeni's address. `push` (`events/stream`) is not used yet.
- Return a cursor with each page or delivery. Opengeni resumes from it and treats `truncated: true` as missed events, which the run says. Repeated `eventId`s are ignored.
- Errors use the extension's codes. Servers built for ChatGPT's earlier sketch of the extension (`capabilities.events` and errors -32011 to -32015) work as well.

```ts
const { source } = await og.createEventSource(workspaceId, { kind: "mcp", serverId: acmeServerId });

await og.createScheduledTask(workspaceId, {
  name: "Tell me when the project changes",
  schedule: { type: "manual" },
  targetSessionId: session.id, // continue this chat
  prompt: "Say what changed in the project and whether it needs me.",
  events: {
    once: true,
    triggers: [{ sourceId: source.id, eventTypes: ["project.updated"], arguments: { projectId } }],
  },
});
```

Each trigger names one event type and its `arguments`, checked against the type's `inputSchema`. Opengeni subscribes as the event source's owner, through their connection to your server, so your server decides which events that person may see just as it does for their tool calls. When no automation listens any more, Opengeni unsubscribes.

### Automations in your UI

`AutomationsPanel` from `@opengeni/react/automations` lists, creates and edits automations inside your own dialog or page. Given a `sessionId`, new automations continue that chat; without one, each run starts a new chat with the workspace's defaults and the owner's access. It offers event triggers whenever the deployment runs them; pass `eventTriggers={false}` to offer schedules only.

```tsx
import { AutomationsPanel } from "@opengeni/react/automations";

<AutomationsPanel
  client={client}
  workspaceId={workspaceId}
  sessionId={chatId}
  eventServers={[{ serverId: acmeServerId, name: "Acme" }]} // offered before a source exists
  argumentDefaults={{ projectId }} // subscription arguments new triggers start with
  onOpenSession={(id) => openChat(id)}
/>;
```

Its words come from the `automations.*` message keys, so `OpenGeniMessagesProvider` translates it. Sessions and session list entries carry `automationWait`: the next run, or the event and source the chat waits for. `sessionAutomationWaitWords(t, session, { now })` turns it into "Waiting for project.updated from Acme" or "Next run: Tomorrow, 09:00" for your own chat list.

### Moving from the first automation API

`@opengeni/sdk/automations`, `@opengeni/sdk/pr-review`, the `/v1/workspaces/:workspaceId/automations/*` and `/pr-review/*` routes, and `POST /v1/webhooks/automations/:endpointId` are deprecated. Their responses carry `Deprecation` and `Sunset` headers; they keep working until January 25, 2027 and are removed in the next major SDK.

- A `signed-json.v1` source becomes a `{ kind: "webhook", adapter: "standard" }` event source. Senders sign with Standard Webhooks and the new secret instead of `x-opengeni-signature-256`.
- A trigger becomes a scheduled task with `events`: its event types carry over, and its session template becomes the task's `agentConfig`.
- Pull-request review becomes a scheduled task on the GitHub source, for `pull_request.opened` and `pull_request.ready_for_review`, with the repositories to review in `agentConfig.resources`. In the web app, **Automations › New › Review new pull requests** sets it up.

## Work until done

Give a session a **goal** and it keeps working across turns until the goal is met or it pauses with a reason:

```ts
agentConfig: {
  prompt: "Reconcile yesterday's refunds.",
  goal: {
    text: "Every refund from yesterday is matched to a ledger entry",
    successCriteria: "A summary lists each refund with its ledger id, or the reason it could not be matched",
  },
}
```

See [Goals](/concepts/goals).

## Bring results back

- **Write back through your tools.** The agent calls your API to update a ticket, post a comment, or store a report. This is the most direct path.
- **Webhooks.** Get notified when a turn completes or fails, a session's status changes, or the agent waits for approval or an answer. Deliveries are signed, at least once, and unordered; read the session through the API when one arrives. See [Webhooks and credentials](/guides/webhooks-and-credentials#webhooks).
- **Read the full output.** `listEvents` returns a summary view that can truncate long answers. For the complete result, call `listEventPage` with `mode: "forensic"` and `payloadMode: "full"`, follow `nextAfter` while `hasMore`, and read `payload.output` from the turn's `turn.completed` event.
