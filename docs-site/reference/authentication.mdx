Sessions belong to workspaces; organization routes manage shared workspaces, keys, and sessions across them. Which credential you use depends on who is calling.

## Choosing a credential

| You are                                              | Use                                                                         |
| ---------------------------------------------------- | --------------------------------------------------------------------------- |
| A product backend integrating OpenGeni               | An **organization API key**                                                 |
| A backend or automation constrained to one workspace | A **workspace API key**                                                     |
| A host acting on behalf of its own signed-in users   | A **delegated access token** signed with the deployment's delegation secret |
| A person in the web console                          | A managed web session (email/password or an enabled Google/GitHub provider) |
| A machine you enrolled                               | The enrollment credential, which the installer manages                      |

## Credentials

| Credential             | Transport                       | Lifetime                 | Notes                                                                                                                                                                 |
| ---------------------- | ------------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Organization API key   | `Authorization: Bearer ogk_...` | Until revoked or expired | Shown once, stored hashed. Explicit permissions across all or selected shared workspaces, or a legacy access tier. Personal workspaces are excluded. Server-side only |
| Workspace API key      | `Authorization: Bearer ogk_...` | Until revoked or expired | Issued by an authorized caller for one workspace; cannot exceed that workspace's grant                                                                                |
| Delegated access token | `Authorization: Bearer ogd_...` | Short, embedded expiry   | HMAC-signed by your host with `OPENGENI_DELEGATION_SECRET`; embeds workspace, account, and permissions                                                                |
| Deployment access key  | `x-opengeni-access-key` header  | Static                   | Optional coarse perimeter enabled by `OPENGENI_AUTH_REQUIRED=true`. Not an identity                                                                                   |
| Managed web session    | Cookie                          | Session                  | Email/password or enabled Google/GitHub sign-in in `managed` mode                                                                                                     |

## Personal sign-in methods

In managed mode, Google, GitHub, and email/password can all sign in the same
user. When a social provider presents an email that matches an existing user,
OpenGeni links it automatically if both emails are verified. Linking keeps the
user's workspaces, history, memberships, and billing. Unverified or different
emails are not linked.

Manage sign-in methods in Personal settings → Security. Sensitive changes
require a recent sign-in, and you must keep at least one method. After you
disconnect a provider, reconnect it from the same page.

Sign-in methods are not integration permissions. Google sign-in does not grant
Gmail or Drive access, and GitHub sign-in does not grant repository access.
Connect those separately.

## Organization key access

An organization key's policy sets both its permissions and its workspace scope:

```ts
const { apiKey, token } = await adminClient.createOrganizationApiKey(organizationId, {
  name: "Tenant reporting",
  policy: {
    preset: "custom",
    permissions: ["workspace:read", "sessions:read", "files:read"],
    workspaceScope: { kind: "selected", workspaceIds: [authorizedWorkspaceId] },
  },
});
// Store token on the server; it is returned only at creation.
```

| Policy preset | Permissions                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `read_only`   | Every read/list/view/search permission except secret values (`secrets:read`, `variable-sets:read`) |
| `full`        | Every non-deprecated permission                                                                    |
| `custom`      | Only the permissions you choose                                                                    |

The preset is a label. The server grants only the permissions you send and
recomputes the label from them. Each permission, including `workspace:admin`,
is granted individually. To give a backend plaintext secret values, add
`secrets:read` or `variable-sets:read` to a custom list.

Scope `{ kind: "all" }` covers every current and future shared workspace in the
organization. `{ kind: "selected", workspaceIds }` takes up to 500 shared
workspace IDs from the same organization. Personal workspaces are never in scope.

Older integrations can keep using the legacy `access` selector:

| `access`            | Use                                                                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `"full"` (default)  | Provision shared workspaces and external members, create and control sessions (including `asUser`), and administer keys                  |
| `"read"`            | Inventory shared workspaces and read their sessions, events, and files for reporting or audit                                            |
| `"developer_setup"` | A restricted tier: workspaces, members, sessions, and usage allowances, but no key management. Setup flows use a full-access key instead |

Omitting both `policy` and `access` creates a full legacy key. Don't combine
`policy` with legacy selectors.

Integrations that provision tenant workspaces, onboard members, and create
sessions as users need all-workspace scope and full permissions.

Keys with `sessions:read` can call `listOrganizationSessions` or
`iterateOrganizationSessions` across their shared workspaces. Personal
workspaces and Only me sessions are excluded.

### Inspect and edit a key

`getOrganizationApiKey(organizationId, apiKeyId)` returns the key's metadata and
policy. `updateOrganizationApiKey(organizationId, apiKeyId, { name?, description?, policy? })`
changes at least one field; `description: null` clears the description. Both
return an `ApiKey` without the token. Only creation returns `{ apiKey, token }`.

A policy edit replaces the whole policy and takes effect on the next request,
without rotating the token. Supplying a policy moves a legacy key to explicit
permissions. Check `apiKey.permissionMode` (`legacy` or `explicit`),
`apiKey.policy`, and `apiKey.workspaceScope`.

### Inspect what a key can do

`getAccessContext()` / `GET /v1/access/me` returns a `credential` object for
requests made directly with an organization or workspace API key. It contains:

- `kind`: `organization_api_key` or `workspace_api_key`
- `access`: `full`, `read`, or `developer_setup` (organization keys only)
- `accountId` and `workspaceId` (null for organization keys)
- `effectiveWorkspacePermissions`
- `policy` and `workspaceScope` (organization keys)

An organization key's `workspaceGrants` may be empty even when it can reach
shared workspaces. Use `listWorkspaces()` to list the workspaces it can reach.

`credential` is absent for `asUser` requests, signed-in users, and delegated
tokens.

## Authenticate users of your chat

`createSessionProxyHandler` and `createChatHandler` call your `resolve(request)` hook on every request. Verify your product's session cookie or bearer there, and return the user's tenant and user ID. The organization key authenticates your backend to OpenGeni; your backend authenticates your users.

A conversation ID is not scoped to a user. Your backend decides which conversations a user may open. An end-user label does not grant workspace membership.

On sign-out or a user or tenant change, abort pending requests, clear transcripts in your frontend, and remount session components. See [Users, tenants & privacy](/integrate/users-and-tenants).

## External-user onboarding

Passing `user` to the chat facade, or calling `asUser` on the SDK, identifies an
external user but does not grant workspace access. Once your backend approves a
user's tenant membership, add the matching workspace member:

```ts
await serviceClient.addExternalWorkspaceMember(authorizedWorkspaceId, {
  identity: { externalId: authenticatedUser.id, source: "my-product" },
  permissions: approvedProductPermissions,
  operationId: persistedOnboardingOperationId,
});
```

Use the same `source` as the chat facade. `approvedProductPermissions` lists the
permissions your product's features need, including the session operations. The
calling key needs `members:manage` and cannot grant more than it holds. User
requests get the intersection of the membership and the key's permissions.

Run this once during onboarding, not on every request. Save the `operationId`
before calling and retry with the same request if the result is uncertain.

## Rules that hold everywhere

- Keep organization keys on your server. Never embed one in a client.
- A delegated token cannot grant more than the host is configured to delegate, and it never reaches a user's Personal workspace.
- A credential for one workspace does not reach another.
- Secrets agents use at runtime (provider tokens, MCP headers, variable sets) are encrypted at rest, readable only with explicit permissions, and never written to audit rows.

## Deployment access modes

| `OPENGENI_PRODUCT_ACCESS_MODE` | Who can call                                                            |
| ------------------------------ | ----------------------------------------------------------------------- |
| `local`                        | The bootstrap `dev` user with broad permissions. Development only       |
| `configured`                   | Delegated bearer tokens from your product, or the deployment shared key |
| `managed`                      | Managed sign-up, organizations, API keys, prepaid credits, and limits   |

Every other credential, including stream tokens, enrollment tokens, sandbox bearers, and signed storage URLs, is listed in the repository's [credentials document](https://github.com/Cloudgeni-ai/opengeni/blob/main/docs/credentials.md).
