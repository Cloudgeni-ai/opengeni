A published app can keep data in Opengeni: collections of JSON records and files. Data belongs to the app, so it survives new versions and rollbacks. There is no server to run and no credential in the app.

## Collections and access

Agents create collections (ask Opengeni, or use the `app_data_define_collection` tool); app code never does. Each collection has an access mode for the people who can open the app:

| Access mode   | People who open the app can            | Good for                     |
| ------------- | -------------------------------------- | ---------------------------- |
| `shared`      | read and change every record           | a team CRM or board          |
| `shared_read` | read; only managers and agents write   | dashboards fed by a schedule |
| `per_viewer`  | read and change only their own records | personal trackers            |
| `append_only` | add records and see only their own     | forms and feedback           |

The app's managers (its owner, workspace admins, and agents acting for them) can read and change everything from the **Data** tab and agent tools, unless a `per_viewer` collection is marked private. The app page itself always acts as a viewer, even for its owner, so a page someone else republished cannot read everyone's records. An **Only me** app's data is reachable only by its owner. Collections can also require unique values (for example one record per email) and validate records with a JSON Schema.

## In app code

```ts
import { createOpenGeniSiteClient } from "@opengeni/sdk/site";

const site = createOpenGeniSiteClient();
const contacts = site.data.collection("contacts");
const { records, nextCursor } = await contacts.list({
  where: [{ field: "company", op: "eq", value: "Acme" }],
  limit: 50,
});
await contacts.insert({ name: "Ada", email: "ada@example.com" });
const file = await site.files.upload(input.files[0], { scope: "private" });
```

Writes take an optional `expectedVersion`, so two people editing the same record get a `conflict` error instead of overwriting each other. Errors are `OpenGeniSiteDataError` with a `code`: `validation`, `conflict`, `not_found`, `forbidden`, `quota_exceeded` or `rate_limited`. Records are written by people who use the app: show them as text, never as HTML.

Pages read data when they load; there are no live updates.

## Agents and schedules

Agents use `app_data_describe`, `app_data_query`, `app_data_write`, `app_data_import`, `app_data_export`, `app_data_reset` and `app_files_*`. A scheduled task runs them with the schedule's access, which makes an app a dashboard that refreshes itself. A conversation started from an app page acts like the page for its whole life: it reaches only that app's data, with viewer rights, even when its owner later continues it from the console.

## Webhooks

Another service can send data into an app: ask the agent to add a webhook to a collection, and give the service the address and secret it shows (once). Each delivery adds or updates records, and automations and workspace webhooks hear about them like any other change. Self-hosted deployments need an API address the service can reach.

## Data syncs

A data sync refills a collection, or one of the app's SQL tables, from a connected tool on a schedule or event, with no model run. Ask Opengeni to set one up (agents use the `app_sync_*` tools). A sync can page through results, and with `removeMissing` it deletes records it wrote that the tool no longer returns.

A personal sync fills each person's own records from their own account. People join from the app: Opengeni lists the personal syncs they haven't joined next to the app, and app code can ask with `site.data.syncs.optIn(id)`. Either way Opengeni shows its own confirmation naming the tool, the account and the collection, and joins only after the person confirms. People with several accounts of the tool choose one. When a personal sync runs on new mail or GitHub activity, each person's own Gmail or GitHub starts it for them.

```ts
const { optedIn } = await site.data.syncs.optIn(syncId); // false if they cancel
const syncs = await site.data.syncs(); // each sync's last run and whether you joined
```

Syncs into SQL tables need app SQL, which self-hosted deployments without the Cloudflare site gateway don't have.

## Limits and usage

By default an app can hold 100 MB of records (256 KB each, each charged an extra 512 bytes), 100,000 records per collection, 50 collections and 1 GB of files (10 MB each), and a workspace 1 GB of app data in total. One request carries at most 4 MB of records. Self-hosted deployments change these with the `OPENGENI_SITE_DATA_*` settings. Writes are rate limited per person and per app (managers and agents share a generous per-app limit), and reads from an app page per person. Usage is recorded for the workspace, which pays for what viewers do; it is not charged yet.

## Managing data

On the app's page, the **Data** tab lists its collections with their access, record counts and size against the limit. Managers can browse records, open a record's JSON, delete a record and export a collection as CSV or JSON.

## Embedding

If you render apps in your own product, pass `fetchResponse` and the app's identity to `createSiteToolBridge` to serve app data; without them app code gets `site_data_unsupported`. See [app data internals](https://github.com/Cloudgeni-ai/opengeni/blob/main/docs/site-data.md).
