# Rigs

An organization, workspace, or organization user can own named **rigs**: versioned setup/check layers over the deployment-owned platform sandbox image (a setup script, self-declared health checks, credential-hook refs, and default variable-set refs). Workspace scope is the compatibility default. Organization rigs are visible across the organization and require account-admin authority to mutate; user rigs follow their owner into every same-organization workspace the owner can currently access. A session **binds** to a rig at creation and **freezes** the rig's currently-active version onto the session row — the rig can gain new versions later without ever moving that session's box out from under it. Agents cannot edit a rig directly; they **propose changes**, which a clean-replay verification run ("rig CI") admits or rejects.

The web creation form asks whether the Rig is for the Organization, the current
Workspace, or Only me; every Rig list row shows that scope. Default Variable
Sets are filtered by compatibility: an organization Rig may reference only
organization sets, a workspace Rig may reference organization or same-workspace
sets, and an Only-me Rig may additionally reference the owner's personal sets.
The server rechecks the same matrix, so a stale or crafted browser request
cannot create a broader dependency than its Rig.

## Invariants

1. **Versions are append-only and definition-immutable.** The definition columns on `rig_versions` (`image`, `setup_script`, checks, credential hooks, default variable sets, changelog, attribution, and version number) are never updated in place. `image` is retained only as historical read compatibility: all current writes store `NULL`, non-null request values are rejected, and runtime ignores older values. Only activation state and version-bound operational `provider_images`/verification metadata may change. Exactly one version per rig can be active at a time (a partial unique index on `(rig_id) WHERE active`). Newly created version 1 and manager-authored direct versions begin inactive and `pending`; only a current version-3 platform-surface receipt bound to the exact immutable provider image, its cold-boot build request, backend, and exact version UUID can activate them. The database enforces that rule for inserts and inactive-to-active transitions, including direct and mixed-version writers. A deferred or failed workflow dispatch is never activation success.
2. **A session's rig binding is immutable in place.** `sessions.rig_id`/`sessions.rig_version_id` are frozen from the explicit `rigId` on create or the workspace's default Rig. A workspace default may be only an active workspace- or organization-scoped Rig; a personal Rig is never valid shared policy, and every inheriting subject must still be able to resolve the selected Rig. Promoting a Rig never moves an existing session. Changing setup after start uses the explicit restart/fork flow below, which creates a fresh singleton destination and leaves the source unchanged. A shared box (`sandbox: 'shared'` or an explicit group) must carry the same frozen `rig_version_id` as the rest of its group; a mismatch 422s at create.
3. **Two change kinds, two trust levels.** `setup_append` is additive (one already-verified-in-a-live-box shell command) and **auto-merges into a new active version on a green clean-replay run** — no `rigs:manage` needed. `definition_edit` is a full next-version edit (script/checks/credential hooks/default variable sets) that still runs the same clean-replay verification but always lands `proposed`; promoting it to a new active version requires `rigs:manage`.
4. **Verification runs in exactly leased, throwaway, secret-free sandboxes.** Rig CI uses the change/version UUID as a canonical `sandbox_leases.sandbox_group_id`, accepts only the `cold -> warming` spawner role, records the exact provider instance, and then reads a versioned manifest of the deployment-owned Browser, Terminal, Computer/Desktop, shell, and launcher bytes through the provider filesystem boundary before any candidate shell command is allowed. It proves command readiness only after that inspection and then commits the instance warm before setup or checks. Platform-owned Browser and Terminal checks, plus Computer/Desktop when enabled, run after Rig setup independently of declared checks. The binary/port probes remain mandatory, then native validation re-reads the candidate manifest around every protected phase while executing trusted commands in fresh provider-owned sidecars created from the pristine deployment runtime authority image. The Terminal sidecar is terminated before a distinct Browser/Computer controller sidecar can be created; neither authority is derived from or reusable through the mutable candidate filesystem. A real interactive root terminal command proves `/workspace` and Bun 1.4.0; a headed BrowserSession lists, opens, and observes a deterministic data URL; and, when desktop is enabled, a ComputerSession lists a real screen, observes it, captures digest-bound nonempty native PNG/JPEG evidence, and performs one benign pointer move. That mutable post-setup receipt is retained only as preflight evidence; it cannot activate or promote a Rig. After platform and declared checks pass, the provider snapshots that exact filesystem as a version-bound immutable image. A second independently leased clean sandbox cold-boots the exact provider image, compares its provider-read runtime manifest byte-for-byte with the pristine deployment manifest before candidate readiness, and only then repeats the content marker, shell checks, native Browser/Terminal/Computer validation, and declared checks. Only this second receipt is activation authority, and every operation is fenced by lease id/epoch, workspace generation, provider instance, exact provider image ID, build request, backend, and Rig version before and after I/O. Enabled `unsupported`, empty targets, invalid images, image-identity or binding drift, runtime-manifest drift, and any session/controller cleanup failure fail verification; only an explicitly disabled Terminal or Computer surface is skipped. Repositories, resources, credentials, variable-set values, archives, session state, and retained processes are never injected. Cleanup quiesces commands before termination and never erases an unconfirmed provider pointer; failed direct cleanup is handed to the ordinary lease reaper.
5. **Explicit authority, physical provenance.** `rigs`, `rig_versions`, and `rig_changes` remain FORCE-RLS. The rig row carries explicit `organization | workspace | user` authority plus its physical origin workspace. User access is derived from the authenticated active organization membership; callers never supply an owner id. An exact attempt may materialize a user rig only through its frozen common-resource grant snapshot, and revalidates owner membership, workspace access, session authority epoch, interruption state, resource/grant generations, and the frozen version before reading the definition. Organization and user authority never widen across organizations.
6. **Rig setup never touches selfhosted.** The rig-setup hook is part of the same owned-hooks block as the repository-clone and credential hooks, which is skipped entirely when the turn's effective sandbox backend is `selfhosted` (a [Connected Machine](connected-machines.md) is the user's own computer; the platform never runs setup against it). A machine-targeted turn therefore always behaves as if rig-less for setup purposes, even when the session carries a rig binding.
7. **Pack selection never bypasses Rig authority.** A v2 Pack installation stores `selected_rig_id`; it does not embed or mutate a Rig version. Pack-created scheduled tasks carry that Rig id, and each resulting session freezes the then-active version through the normal session-creation boundary.

## Configuration

- `OPENGENI_RIG_SETUP_TIMEOUT_MS` — the budget for the rig's own setup script, separate from the general 120s sandbox-lifecycle-hook default. Defaults to 600000 (10 minutes). Applies to both a live turn's setup hook and a rig-CI verification run.
- `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED` — default `false`. When false, rig CI fails before lease acquire/provider create rather than falling back to an unowned sandbox. Enable only after every worker capable of running the global sandbox reaper has the matching pre-termination lease revalidation behavior; see [Operational rollout](#operational-rollout).
- No dedicated encryption key: a rig's `setupScript`/`checks` are not secret material — secrets are attached only via the rig's `defaultVariableSetIds`, which reference scoped Variable Sets visible from the rig's workspace and are subject to their own encryption (see [`variable-sets.md`](variable-sets.md)). Historical `image` values are inert metadata, not executable configuration.

## Rig setup at runtime

When a session's frozen rig version carries a non-empty `setupScript`, the worker threads a `rigSetup` descriptor (rig id, version id, exact provider-image content hash, script, `rigSetupTimeoutMs`) into the agent build. The resulting `rig-setup` sandbox lifecycle hook runs **first** among the `beforeAgentStart` hooks — before credential hooks and the repository-clone hook — so any tooling it installs is available to what follows. The hook is idempotent and **marker-guarded**: it writes and runs the script under coreutils `timeout` once per box, then records the successful version and exact content hash under box-local `/tmp/opengeni/rig-setup`. Small scripts use one collision-safe heredoc; larger contract-valid scripts first run one compact marker probe, then transfer only an uncached script in bounded base64 chunks to a mode-0700 temporary payload and remove it after execution. This keeps provider command frames bounded and makes a verified-image cache hit independent of setup-script size. These markers deliberately stay outside `/workspace`, because a workspace archive can be restored onto a fresh machine whose packages are not installed. A fresh box created from a matching verified provider image instead carries a read-only content proof under `/var/opengeni`; runtime reads that proof but never needs to write into the image-owned directory. A warm box re-entering the hook skips a script that already succeeded; a failed/timed-out run retries next turn. Concurrent turn holders on the same shared box coordinate through a lock directory so only one of them actually runs the script, and marker/lock storage failures fail immediately rather than being misreported as setup timeouts. Three runtime events narrate the outcome: `rig.setup.started`, then exactly one of `rig.setup.completed`, `rig.setup.skipped` (marker already present), or `rig.setup.failed` (nonzero exit or timeout — **fails the turn closed**).

### Platform base and provider-image optimization

Every Rig-bound managed sandbox uses the deployment's `OPENGENI_DOCKER_IMAGE`/`OPENGENI_MODAL_IMAGE_REF` as its logical base. Public Rig create/version/change contracts reject `image`, new versions store `NULL`, and historical non-null values are ignored at runtime. A pre-v2 Pack image is also bypassed when the session is Rig-bound, so it cannot replace the platform base beneath Rig setup. Rig-less pre-v2 Pack rows retain their historical direct image path only for rollback compatibility. V2 Pack manifests that still require `sandboxImage` are blocked until they are migrated to the platform base.

Pre-v2 Pack installation rows have neither a manifest snapshot nor a manifest digest. A v2 Pack install/update migrates to explicit Rig/component runtime and cannot combine both models for the same installation. See [`packs.md`](packs.md).

After the deployment base resolves, a genuinely fresh Docker or Modal creation may select the version's backend-matching `providerImages.<backend>.imageId` only when its status is `ready`, it carries current version-3 independent cold-boot proof, and its backend, deployment source image, setup hash, and full definition/content hash still match the frozen version. Modal additionally requires the current authenticated workspace/environment to hash to the same provider binding recorded at verification; Docker image IDs are daemon-local physical identities and carry no Modal binding. Unchanged versions therefore reuse one immutable provider image. Missing, version-1/version-2 legacy-unproven, non-ready, unsupported, malformed, binding-mismatched, or content-mismatched records cannot admit or reactivate a version under the current protocol. Historical already-active versions may still take the ordinary runtime-setup path when no eligible optimization exists. The provider build-request identity uses a new v4 domain separator, so rebuilding under the current proof protocol cannot resolve to a provider object admitted by a prior protocol. If Docker or Modal authoritatively reports that a selected immutable image no longer exists during fresh creation, the same attempt retries once from the exact pre-optimization logical settings and records both create outcomes; without that exact logical identity it fails closed rather than booting a provider default. The provider image ID is used only for physical cold creation: the deployment OCI/base identity remains on the lease and is the independent source-content fence, so worker, Browser, Computer, Terminal, and API-direct calls cannot disagree merely because one path knows the provider-native image ID.

`RigVersion.providerImages` is observable build truth keyed by backend: `building | ready | failed | unsupported`, immutable image ID/digest, source/setup/content hashes, deterministic provider request UUID, durable checkpoint-artifact ownership where applicable, hashed provider binding where applicable, versioned cold-boot proof, verification provenance, timestamps, and bounded failure detail. Modal implements the build through its immutable filesystem snapshot API. The snapshot is registered immediately in the provider-artifact ledger, then independently cold-booted before publication; ready rig/change references protect it from global GC, while failed, rejected, superseded, abandoned, or deleted targets become reclaimable through the ordinary bounded checkpoint collector. Docker commits the exact running verifier container under a deterministic request tag, verifies ownership labels and the resulting immutable daemon image ID, and independently cold-boots that exact ID before publication. A retry after an ambiguous Docker acknowledgement resolves only the same labeled request tag; it cannot adopt another build's image. A timeout, cancellation, transport failure, or malformed response after dispatch leaves a separate durable cleanup obligation as `outcome_unknown`; source teardown retries only the exact caller-owned request against the original sandbox and provider binding, records any late provider object before termination, and hands externally managed artifacts to the bounded collector. A structurally typed, authoritative provider refusal such as invalid arguments, missing capability, authentication, or permission denial transitions the obligation to terminal `build_failed` and cannot block source teardown; message text alone is never terminal authority. Every other backend truthfully records or behaves as unsupported until it implements both build and independent validation.

Fresh-create latency remains an observed SLO, not a code-level promise. The existing `opengeni_sandbox_create_duration_seconds` histogram now carries the bounded `image_source="provider_immutable" | "logical"` label, allowing staging to compare Modal provider-image p50/p95 against the current targets (p50 ≤ 12 seconds, p95 ≤ 20 seconds). This implementation does not claim those thresholds until representative deployed samples exist.

### Credential hooks

`credentialHooks` on a rig version are string ids resolved against the same built-in sandbox-lifecycle-hook registry as the deployment's `OPENGENI_SANDBOX_PREPARATION_PROFILES` hooks (currently `azure-cli-login`); an unknown id throws at per-turn build time, not silently. They are **unioned** with the deployment's profile-driven hooks, deduped by id, with the deployment hooks keeping their leading position — a rig can add credential setup a deployment profile doesn't already provide, but never removes one the deployment declares.

### Default variable sets

A rig version's `defaultVariableSetIds` are decrypted and merged in listed order, then layered **below** the session's ordered explicit Variable Sets in the env-injection chain:

```
deployment allowlist < git identity < ordered Rig defaults < ordered explicit session sets < run-scoped GitHub auth
```

A later entry wins on a name collision. Rig defaults preserve their listed order; explicit session sets then preserve their own listed order, so any explicit session entry overrides an earlier Rig default with the same variable name. Scope never changes precedence. See [`variable-sets.md`](variable-sets.md) for the rest of that layering (permissioned secret access, exact content, reserved names, and the managed-sandbox-only scope).

### Agent-visible doctrine

A rig-bound turn's system instructions carry a non-bypassable doctrine block (composed into the CORE, so a white-labelled persona template can never drop it) naming the rig and active version and telling the agent: its sandbox is an ephemeral fork that dies with the box, a durable change needs `rig_propose_change` with the exact command that already worked, and `rig_get` shows the rig's current setup/checks before reinstalling anything.

### Default rig resolution

A session's rig binding resolves at create as: the explicit `rigId` on the create payload if given, else the workspace's `default_rig_id` (`workspaces.default_rig_id`), else rig-less. An explicit unknown/inactive `rigId` is a caller error (422). A stale workspace-default (deleted rig, or one somehow left with no active version) degrades silently to rig-less rather than failing the create. There is currently no API or web-console surface to set `default_rig_id` — it is a schema column consumed by session creation with no write path yet.

Pack installation is another producer of the existing explicit `rigId`, not another resolution rule. Installation preview validates the selected Rig, blocks legacy `sandboxImage` requirements while explicit Rig images are disabled, optionally requires verified health, stores the Rig id on the Pack installation, and copies it into Pack-created scheduled tasks. Session creation still owns active-version lookup and freezing.

### Changing setup after a session starts

OpenGeni does not hot-swap a Rig on a live session or mutate the current box in place. The web inspector's **Restart with setup** action uses `POST /v1/workspaces/:workspaceId/sessions/:sessionId/forks` with optional `rigId` and ordered `variableSetIds`. The operation requires the ordinary tenancy-fork permissions plus `rigs:use` when a Rig is selected and both Variable Set attachment permissions for every selected/default set.

The database creates the history fork and configures its runtime in one transaction. The destination receives a fresh root/sandbox-group identity, freezes the selected Rig's then-active version, stores the ordered explicit Variable Sets, emits `session.created` and `session.runtime.configured`, and starts with no active sandbox. Any validation or configuration failure rolls back the fork and its idempotency receipt. Exact retries recover both committed events without consulting mutable source-session visibility or the Rig's newly active version. The source session and any source sandbox remain unchanged.

## Verification and change promotion (rig CI)

Every proposed change is verified the same way, in a throwaway sandbox with no attached secrets:

For direct version verification, the database first commits an opaque UUID attempt token, execution generation `1`, and the expected active-version compare-and-swap value. REST and MCP keep the stable logical `rig-verification-version-<versionId>-attempt-<attemptId>` identity. Temporal starts the immutable physical ID `<logicalId>-generation-<executionGeneration>` with `REJECT_DUPLICATE`, and the workflow, activity, lease holder, success, failure, and promotion fence all carry that exact attempt-plus-generation pair. Exact version selection is manager-only because it can create or supersede an attempt and eventually activate that historical version. The use-authorized recovery operation accepts no version identity and resolves only exactly one inactive version whose attempt is already durably `pending`; zero or ambiguous candidates fail closed. Recovery never mints a new logical attempt. A duplicate running or non-failed terminal physical run is an idempotent dispatch acknowledgement. When the exact physical run is `FAILED`, one row-locked compare-and-swap advances the generation and all concurrent callers converge on the next physical ID. A deliberate manager-authored newer attempt still supersedes the whole logical token, while any late writer from an older attempt or execution generation becomes a no-op.

1. Acquire the canonical sandbox lease keyed by the change UUID (or version UUID for an active-version recheck), using a deterministic holder derived from the target, logical attempt, and execution generation, the candidate's effective backend/image, and a bounded 20-minute lease/warming TTL. Only the `spawner` role is valid: `attached`, `rearmed`, or `fenced` means this run cannot prove a clean box and fails without reuse. Lease contention never writes a terminal verification failure; the still-pending logical attempt can advance to a later physical generation after the failed Temporal run is observed. The activity touches its holder every 10 seconds until cleanup.
2. Establish a fresh sandbox session (`rig-verification-<changeId>-...` or `rig-version-verification-<versionId>-...`). The create callback retains the exact handle before any await, persists the provider instance on the warming lease, and best-effort tags Modal with the same lease identity. Modal stores an exact instance pointer with no resume envelope; other resumable backends store their serialized envelope.
3. Prove provider command readiness within the shared 60-second post-create/restore budget, then commit the warming lease to warm under its epoch fence **before** verifier work. A failed or acknowledgement-ambiguous probe/commit fails closed; cleanup tries the mutually exclusive warming and warm exact-fenced transitions after provider termination.
4. If the candidate version has a non-empty `setupScript`, run the rig-setup hook against it. For a `setup_append` change, then run the proposed command; a nonzero exit rejects the change immediately without running the declared checks.
5. Run the platform-owned Browser/Terminal/Computer checks, then every declared check (`RigCheck.command`), recording their `exitCode`/`output` separately before classifying the outcome.
6. After checks pass, compute the exact backend/deployment-source/definition content identity and ask the provider registry to build one immutable image from the same clean verifier sandbox. Register its provider object immediately, then cold-boot that exact image in a second independently owned sandbox and re-run the exact content marker, platform-owned checks, native platform-surface validation, and every declared check. The provider adapter discovers the immutable identity from that live instance; a caller-supplied expected ID is assertion-only and can never redirect validation to a pristine base image. Only the exact-image receipt can finalize the image ready and activate/promote the target. Direct version verification claims/finalizes the backend slot under a row lock and deterministic provider request UUID; retries converge on the same byte-identical provider operation, older proof records rebuild, and stale-content conflicts fail closed. Change verification carries only a finalized, current-proof, hash-matching record with exact change provenance into the newly promoted version. Provider-image failure, in-progress state, or unsupported capability is recorded truthfully and leaves the verification failed/inactive.
7. In `finally`, cancel and wait for every verifier-owned command before provider teardown. If direct termination is confirmed, clear the exact warm/warming pointer under the epoch fence. A failed or expired warming transition advances the lease epoch before a successor can reacquire, so a non-abortable old create cannot record, commit, fail, or clean up against the successor even when the old numeric epoch would otherwise match. Always release the holder with a minimal drain grace; if termination or DB cleanup is inconclusive, retain the provider pointer so the ordinary reaper retries instead of manufacturing an orphan.

The Temporal activity heartbeats every 10 seconds, reserves up to two minutes of its 15-minute start-to-close budget for cleanup, and uses `WAIT_CANCELLATION_COMPLETED` so workflow cancellation does not report completion before the physical command/provider fence has run.

| Kind              | Checks passed? | Infra error? | Outcome                                                                                                                                                      |
| ----------------- | -------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `setup_append`    | yes            | no           | `merged` — a new version is minted from the base version with the command appended to `setupScript`, and activated automatically. No `rigs:manage` involved. |
| `definition_edit` | yes            | no           | `proposed` (verification recorded, `verification.passed = true`) — awaits an explicit `rigs:manage` promote.                                                 |
| either            | no             | no           | `rejected`.                                                                                                                                                  |
| either            | —              | yes          | `failed` (retryable — establishing the sandbox, running a command, or persisting state threw).                                                               |

A `definition_edit` promote (`POST .../changes/:changeId/promote`) re-validates that the change is `proposed` with `verification.passed === true`, a finalized current-protocol provider-image record with exact change provenance, and a receipt whose backend, provider image ID, build-request sandbox group, and `rigVersionId = changeId` all match that record. Both promotion paths (`setup_append` auto-merge and `definition_edit` explicit promote) use the change UUID as the promoted version UUID and store that exact unchanged receipt as the version's passed proof. Deactivation, the active insert, and the change's merged/result-version transition commit in one transaction, so a rig never exposes an unproved promoted version. Audit writes happen after that durable terminal state; an audit failure remains an activity failure but cannot rewrite a passed active version to failed.

Provider images are not workspace archives or restore points. They contain only the clean verified base filesystem plus rig setup, are selected only for fresh provider creation, and never carry repository contents, session resources, credentials, variable-set values, archives, session state, or processes. Existing lease recovery, archive capture/hydration, warm resume, selfhosted routing, and reaper ownership remain separate and authoritative.

Rig audit events (`rig.change.proposed`, `rig.verification.started`/`.passed`/`.failed`, `rig.change.merged`/`.rejected`/`.failed`, `rig.version.activated`/`.promoted`) are recorded through the standard workspace audit log for every step above.

### Operational rollout

Migration `0393_fail_closed_rig_version_activation.sql` is a one-way maintenance cutover. Stop every API, control worker, and turn worker for the target database, supply the exact old/new runtime login list to the migrator, apply 0393 from the new image, and restart only that image generation. The migration adds version verification state without claiming old rows passed, changes `create_scoped_rig`'s omitted activation default to inactive, rejects every active insert or inactive-to-active transition without a current exact receipt and matching ready provider-image record, removes complete version-1/version-2 provider-image artifact references so GC can collect obsolete artifacts, and rejects a stale finalizer that tries to reintroduce an obsolete ready proof. Existing active versions are grandfathered; updates that do not newly activate a row remain available after the cutover.

After 0393 commits, never restart a pre-0393 application image or attempt a mixed-version rollback. Remain in maintenance and fix forward. Do not drop the triggers, restore the old active-by-default function, or synthesize passed receipts/provider-image records; each would reopen the writer-protocol vulnerability. Obsolete provider-artifact references are released to normal GC.

Lease-aware rig verification and destructive Modal orphan revalidation are one rollout contract, but the verifier is intentionally activated separately:

1. Pause rig-verification dispatch. Deploy the worker revision containing canonical verifier leases and the Modal orphan sweep's immediate pre-terminate durable re-read, with `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED=false`.
2. Prove every worker consuming the shared reaper/rig-verification queues is on that revision. Then enable `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED=true` as a separate configuration change and resume dispatch.

Rollback is the reverse safety order: disable the flag first, drain/stop verifier dispatch, wait until no active verifier lease remains, and only then roll the worker back. A mixed fleet must never create owned verifier boxes that an older orphan reaper cannot recognize. Disabling the flag never falls back to the legacy unleased path.

## Composition with variable sets

A rig's `defaultVariableSetIds` reference scoped Variable Sets visible to the initiating subject from the rig's workspace. Changing that field, including clearing it, requires `variable-sets:attach`; a non-empty value additionally requires `variable-sets:use` and validates every reference at rig create/edit/change-propose time. Organization- and user-scoped sets may originate in another workspace in the same organization when their scoped authority makes them visible; unknown, inaccessible, workspace-scoped foreign, and cross-organization ids remain indistinguishable and 422. Binding any Rig version with defaults to a session independently re-requires both permissions and revalidates each referenced set for the initiating subject, including when the Rig came from the workspace default or a post-start restart. They are pure references: a Rig never stores variable values itself, and deleting a Variable Set that a Rig still references is unaffected by the Rig (Variable Set deletion semantics are governed entirely by [`variable-sets.md`](variable-sets.md#deletion-semantics), not by Rig references). At runtime the Rig's default sets are decrypted and merged in listed order, then the session's ordered explicit sets are layered on top in listed order — see [Default variable sets](#default-variable-sets) above.

## MCP surface

The first-party MCP server exposes rig tools, gated by the same permissions as the REST routes and **registered only for grants that hold them**:

- `rig_list` (`rigs:use`) — workspace rigs and their active versions.
- `rig_get` (`rigs:use`) — one rig with one bounded active definition plus
  compact-by-query historical version/change summaries. The complete
  pretty-printed MCP result is capped at 64 KiB. Historical setup scripts,
  check bodies, change payloads, and verification logs are not copied into
  model context; totals, counts, byte facts, previews, and truncation facts make
  the omission explicit. `versionLimit` and `changeLimit` independently bound
  the two histories (default 20, maximum 100). The access-controlled REST
  version/change detail routes above remain the exact retained-detail surface.
- `rig_propose_change` (`rigs:use`) — propose an additive `setup_append` change (the exact command that already worked in this sandbox) and start verification. On a session-scoped call this attributes the change to `session:<sessionId>` rather than the caller's user subject.
- `rig_verify` (`rigs:use`) — trigger verification: pass `changeId` to (re-)verify a proposed change, pass `recoverDeferredVersion: true` to resume the one unique inactive `pending` version without selecting it or creating a new attempt, or omit both to re-verify the active version's checks. `changeId` and `recoverDeferredVersion` are mutually exclusive. Zero or ambiguous recovery candidates fail closed; dispatch uncertainty returns a truthful partial-failure receipt that preserves the same attempt for retry.
- `rig_promote` (`rigs:manage`) — promote a verified `definition_edit` change to a new active version. **Not registered for a default sandboxed-agent session**: the worker's default first-party delegated token carries `rigs:use` but not `rigs:manage`, so an agent can propose and get changes verified but cannot itself promote a `definition_edit`. An explicitly scoped owner session may carry `rigs:manage`. A `setup_append` change needs no promote tool at all: a green clean-replay run merges it automatically.

## Deletion and rollback semantics

- **Delete.** `DELETE .../rigs/:rigId` 409s while any session still references the rig (`sessions.rig_id`); there is no cascade-detach — retire or wait out the referencing sessions first, then delete.
- **Rollback.** There is no "revert" operation distinct from activation: `POST .../versions/:versionId/activate` flips the active flag to any existing version (older or newer) without minting new content or touching version rows. A rollback is exactly that call against an older version id.
- **A session's binding never moves.** Activating a different version — whether via rollback or a fresh promote — changes what _new_ sessions and re-verification see as "the active version"; it never migrates an already-bound session's frozen `rig_version_id`. A session that wants the newer (or rolled-back) version must be recreated.
