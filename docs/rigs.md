# Sandbox Environments

A Sandbox Environment defines custom setup and checks; it is not a running
sandbox or a Variable Set. The product name has changed, but API routes and
identifiers such as `/rigs`, `rigId`, `rigVersionId`, and `rig_get` stay unchanged.

An organization, workspace, or organization user can own named **sandbox environments**: versioned setup/check layers over the deployment-owned platform sandbox image (a setup script, self-declared health checks, credential-hook refs, and default variable-set refs). Workspace scope is the compatibility default. Organization sandbox environments are visible across the organization and require account-admin authority to mutate; user sandbox environments follow their owner into every same-organization workspace the owner can currently access. A session **binds** to a sandbox environment at creation and **freezes** the sandbox environment's currently-active version onto the session row — the sandbox environment can gain new versions later without ever moving that session's box out from under it. Agents cannot edit a sandbox environment directly; they **propose changes**, which a clean-replay verification run ("sandbox environment CI") admits or rejects.

The web creation form asks whether the Sandbox Environment is for the Organization, the current
Workspace, or Only me; every Sandbox Environment list row shows that scope. Default Variable
Sets are filtered by compatibility: an organization Sandbox Environment may reference only
organization sets, a workspace Sandbox Environment may reference organization or same-workspace
sets, and an Only-me Sandbox Environment may additionally reference the owner's personal sets.
The server rechecks the same matrix, so a stale or crafted browser request
cannot create a broader dependency than its Sandbox Environment.

## Invariants

1. **Versions are append-only and definition-immutable.** The definition columns on `rig_versions` (`image`, `setup_script`, checks, credential hooks, default variable sets, changelog, attribution, and version number) are never updated in place. `image` is retained only as historical read compatibility: all current writes store `NULL`, non-null request values are rejected, and runtime ignores older values. Only activation state and version-bound operational `provider_images` build metadata may change. Exactly one version per sandbox environment can be active at a time (a partial unique index on `(rig_id) WHERE active`).
2. **A session's sandbox environment binding is immutable in place.** `sessions.rig_id`/`sessions.rig_version_id` are frozen from the explicit `rigId` on create or the workspace's default Sandbox Environment. Promoting a Sandbox Environment never moves an existing session. Changing setup after start uses the explicit restart/fork flow below, which creates a fresh singleton destination and leaves the source unchanged. A shared box (`sandbox: 'shared'` or an explicit group) must carry the same frozen `rig_version_id` as the rest of its group; a mismatch 422s at create.
3. **Two change kinds, two trust levels.** `setup_append` is additive (one already-verified-in-a-live-box shell command) and **auto-merges into a new active version on a green clean-replay run** — no `rigs:manage` needed. `definition_edit` is a full next-version edit (script/checks/credential hooks/default variable sets) that still runs the same clean-replay verification but always lands `proposed`; promoting it to a new active version requires `rigs:manage`.
4. **Verification runs in exactly leased, throwaway, secret-free sandboxes.** Sandbox Environment CI uses the change/version UUID as a canonical `sandbox_leases.sandbox_group_id`, accepts only the `cold -> warming` spawner role, records the exact provider instance, proves command readiness, and only then commits it warm before setup or checks. Platform-owned Browser and Terminal checks, plus Computer/Desktop when enabled, run after Sandbox Environment setup independently of declared checks. They start and probe the canonical services on ports 7682, 7681, and 6080 and tear them down before snapshotting. After both platform and declared checks pass, a backend may snapshot that clean filesystem once as a version-bound immutable image. A second independently leased clean sandbox must cold-boot the exact image and pass its content marker, the same platform checks, and declared checks before the image becomes selectable. Repositories, resources, credentials, variable-set values, archives, session state, and retained processes are never injected. Cleanup quiesces commands before termination and never erases an unconfirmed provider pointer; failed direct cleanup is handed to the ordinary lease reaper.
5. **Explicit authority, physical provenance.** `rigs`, `rig_versions`, and `rig_changes` remain FORCE-RLS. The sandbox environment row carries explicit `organization | workspace | user` authority plus its physical origin workspace. User access is derived from the authenticated active organization membership; callers never supply an owner id. An exact attempt may materialize a user sandbox environment only through its frozen common-resource grant snapshot, and revalidates owner membership, workspace access, session authority epoch, interruption state, resource/grant generations, and the frozen version before reading the definition. Organization and user authority never widen across organizations.
6. **Sandbox Environment setup never touches selfhosted.** The sandbox environment-setup hook is part of the same owned-hooks block as the repository-clone and credential hooks, which is skipped entirely when the turn's effective sandbox backend is `selfhosted` (a [Connected Machine](connected-machines.md) is the user's own computer; the platform never runs setup against it). A machine-targeted turn therefore always behaves as if sandbox environment-less for setup purposes, even when the session carries a sandbox environment binding.

## Configuration

- `OPENGENI_RIG_SETUP_TIMEOUT_MS` — the budget for the sandbox environment's own setup script, separate from the general 120s sandbox-lifecycle-hook default. Defaults to 600000 (10 minutes). Applies to both a live turn's setup hook and a sandbox environment-CI verification run.
- `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED` — default `false`. When false, sandbox environment CI fails before lease acquire/provider create rather than falling back to an unowned sandbox. Enable only after every worker capable of running the global sandbox reaper has the matching pre-termination lease revalidation behavior; see [Operational rollout](#operational-rollout).
- No dedicated encryption key: a sandbox environment's `setupScript`/`checks` are not secret material — secrets are attached only via the sandbox environment's `defaultVariableSetIds`, which reference scoped Variable Sets visible from the sandbox environment's workspace and are subject to their own encryption (see [`variable-sets.md`](variable-sets.md)). Historical `image` values are inert metadata, not executable configuration.

## Sandbox Environment setup at runtime

When a session's frozen sandbox environment version carries a non-empty `setupScript`, the worker threads a `rigSetup` descriptor (sandbox environment id, version id, exact provider-image content hash, script, `rigSetupTimeoutMs`) into the agent build. The resulting `rig-setup` sandbox lifecycle hook runs **first** among the `beforeAgentStart` hooks — before credential hooks and the repository-clone hook — so any tooling it installs is available to what follows. The hook is idempotent and **marker-guarded**: it writes and runs the script under coreutils `timeout` once per box, then records the successful version and exact content hash under box-local `/tmp/opengeni/rig-setup`. Small scripts use one collision-safe heredoc; larger contract-valid scripts first run one compact marker probe, then transfer only an uncached script in bounded base64 chunks to a mode-0700 temporary payload and remove it after execution. This keeps provider command frames bounded and makes a verified-image cache hit independent of setup-script size. These markers deliberately stay outside `/workspace`, because a workspace archive can be restored onto a fresh machine whose packages are not installed. A fresh box created from a matching verified provider image instead carries a read-only content proof under `/var/opengeni`; runtime reads that proof but never needs to write into the image-owned directory. A warm box re-entering the hook skips a script that already succeeded; a failed/timed-out run retries next turn. Concurrent turn holders on the same shared box coordinate through a lock directory so only one of them actually runs the script, and marker/lock storage failures fail immediately rather than being misreported as setup timeouts. Three runtime events narrate the outcome: `rig.setup.started`, then exactly one of `rig.setup.completed`, `rig.setup.skipped` (marker already present), or `rig.setup.failed` (nonzero exit or timeout — **fails the turn closed**).

### Platform base and provider-image optimization

Every Sandbox Environment-bound managed sandbox uses the deployment's `OPENGENI_DOCKER_IMAGE`/`OPENGENI_MODAL_IMAGE_REF` as its logical base. Public Sandbox Environment create/version/change contracts reject `image`, new versions store `NULL`, and historical non-null values are ignored at runtime.


After the deployment base resolves, a genuinely fresh Modal creation may select the version's `providerImages.modal.imageId` only when its status is `ready`, it carries versioned independent cold-boot proof, its backend, deployment source image, setup hash, and full definition/content hash still match the frozen version, and the current authenticated Modal workspace/environment hashes to the same provider binding recorded at verification. Unchanged versions therefore reuse one immutable provider image. Missing, legacy-unproven, non-ready, unsupported, malformed, binding-mismatched, or content-mismatched records leave the logical image untouched and retain the ordinary runtime-setup path. If Modal authoritatively reports that a selected immutable image no longer exists during fresh creation, the same attempt retries once from the exact pre-optimization logical settings (including an ID-only logical base) and records both create outcomes; without that exact identity it fails closed rather than booting a provider default. The provider image ID is used only for physical cold creation: the deployment OCI/base identity remains on the lease, so worker, Browser, Computer, Terminal, and API-direct calls cannot disagree merely because one path knows the provider-native image id.

`RigVersion.providerImages` is observable build truth keyed by backend: `building | ready | failed | unsupported`, immutable image ID/digest, source/setup/content hashes, deterministic provider request UUID, durable checkpoint-artifact ownership, hashed provider binding, versioned cold-boot proof, verification provenance, timestamps, and bounded failure detail. Modal currently implements the build operation through its immutable filesystem snapshot API. The snapshot is registered immediately in the provider-artifact ledger, then independently cold-booted before publication; ready sandbox environment/change references protect it from global GC, while failed, rejected, superseded, abandoned, or deleted targets become reclaimable through the ordinary bounded checkpoint collector. Every other backend truthfully records or behaves as unsupported until it implements both build and independent validation.

Fresh-create latency remains an observed SLO, not a code-level promise. The existing `opengeni_sandbox_create_duration_seconds` histogram now carries the bounded `image_source="provider_immutable" | "logical"` label, allowing staging to compare Modal provider-image p50/p95 against the current targets (p50 ≤ 12 seconds, p95 ≤ 20 seconds). This implementation does not claim those thresholds until representative deployed samples exist.

### Credential hooks

`credentialHooks` on a sandbox environment version are string ids resolved against the same built-in sandbox-lifecycle-hook registry as the deployment's `OPENGENI_SANDBOX_PREPARATION_PROFILES` hooks (currently `azure-cli-login`); an unknown id throws at per-turn build time, not silently. They are **unioned** with the deployment's profile-driven hooks, deduped by id, with the deployment hooks keeping their leading position — a sandbox environment can add credential setup a deployment profile doesn't already provide, but never removes one the deployment declares.

### Default variable sets

A sandbox environment version's `defaultVariableSetIds` are decrypted and merged in listed order, then layered **below** the session's ordered explicit Variable Sets in the env-injection chain:

```
deployment allowlist < git identity < ordered sandbox environment defaults < ordered explicit session sets < run-scoped GitHub auth
```

A later entry wins on a name collision. Sandbox Environment defaults preserve their listed order; explicit session sets then preserve their own listed order, so any explicit session entry overrides an earlier Sandbox Environment default with the same variable name. Scope never changes precedence. See [`variable-sets.md`](variable-sets.md) for the rest of that layering (permissioned secret access, exact content, reserved names, and the managed-sandbox-only scope).

### Agent-visible doctrine

A sandbox environment-bound turn's system instructions carry a non-bypassable doctrine block (composed into the CORE, so a white-labelled persona template can never drop it) naming the sandbox environment and active version and telling the agent: its sandbox is an ephemeral fork that dies with the box, a durable change needs `rig_propose_change` with the exact command that already worked, and `rig_get` shows the sandbox environment's current setup/checks before reinstalling anything.

### Default sandbox environment resolution

A session's sandbox environment binding resolves at create as: the explicit `rigId` on the create payload if given, else the workspace's `default_rig_id` (`workspaces.default_rig_id`), else sandbox environment-less. An explicit unknown/inactive `rigId` is a caller error (422). A stale workspace-default (deleted sandbox environment, or one somehow left with no active version) degrades silently to sandbox environment-less rather than failing the create. There is currently no API or web-console surface to set `default_rig_id` — it is a schema column consumed by session creation with no write path yet.


### Changing setup after a session starts

OpenGeni does not hot-swap a Sandbox Environment on a live session or mutate the current box in place. The web inspector's **Restart with setup** action uses `POST /v1/workspaces/:workspaceId/sessions/:sessionId/forks` with optional `rigId` and ordered `variableSetIds`. The operation requires the ordinary tenancy-fork permissions plus `rigs:use` when a Sandbox Environment is selected and both Variable Set attachment permissions for every selected/default set.

The database creates the history fork and configures its runtime in one transaction. The destination receives a fresh root/sandbox-group identity, freezes the selected Sandbox Environment's then-active version, stores the ordered explicit Variable Sets, emits `session.created` and `session.runtime.configured`, and starts with no active sandbox. Any validation or configuration failure rolls back the fork and its idempotency receipt. Exact retries recover both committed events without consulting mutable source-session visibility or the Sandbox Environment's newly active version. The source session and any source sandbox remain unchanged.

## Verification and change promotion (sandbox environment CI)

Every proposed change is verified the same way, in a throwaway sandbox with no attached secrets:

1. Acquire the canonical sandbox lease keyed by the change UUID (or version UUID for an active-version recheck), using the candidate's effective backend/image and a bounded 20-minute lease/warming TTL. Only the `spawner` role is valid: `attached`, `rearmed`, or `fenced` means this run cannot prove a clean box and fails without reuse. The activity touches its holder every 10 seconds until cleanup.
2. Establish a fresh sandbox session (`rig-verification-<changeId>-...` or `rig-version-verification-<versionId>-...`). The create callback retains the exact handle before any await, persists the provider instance on the warming lease, and best-effort tags Modal with the same lease identity. Modal stores an exact instance pointer with no resume envelope; other resumable backends store their serialized envelope.
3. Prove Modal command readiness within the shared 60-second post-create/restore budget, then commit the warming lease to warm under its epoch fence **before** verifier work. A failed or acknowledgement-ambiguous probe/commit fails closed; cleanup tries the mutually exclusive warming and warm exact-fenced transitions after provider termination.
4. If the candidate version has a non-empty `setupScript`, run the sandbox environment-setup hook against it. For a `setup_append` change, then run the proposed command; a nonzero exit rejects the change immediately without running the declared checks.
5. Run the platform-owned Browser/Terminal/Computer checks, then every declared check (`RigCheck.command`), recording their `exitCode`/`output` separately before classifying the outcome.
6. After checks pass, compute the exact backend/deployment-source/definition content identity and ask the provider registry to build one immutable image from the same clean verifier sandbox. Register its provider object immediately, then cold-boot that exact image in a second independently owned sandbox and re-run the exact content marker, platform-owned checks, and every declared check. Only then finalize it ready with `coldBootValidation`. Direct version verification claims/finalizes the backend slot under a row lock and deterministic provider request UUID; retries converge on the same byte-identical provider operation, older protocol/content records rebuild, and stale-content conflicts fail closed. Change verification carries only a finalized hash-matching record into the newly promoted version. Provider-image failure or unsupported capability is recorded truthfully but does not turn a correctly verified sandbox environment definition into a failed verification—the runtime setup fallback remains authoritative.
7. In `finally`, cancel and wait for every verifier-owned command before provider teardown. If direct termination is confirmed, clear the exact warm/warming pointer under the epoch fence. A failed or expired warming transition advances the lease epoch before a successor can reacquire, so a non-abortable old create cannot record, commit, fail, or clean up against the successor even when the old numeric epoch would otherwise match. Always release the holder with a minimal drain grace; if termination or DB cleanup is inconclusive, retain the provider pointer so the ordinary reaper retries instead of manufacturing an orphan.

The Temporal activity heartbeats every 10 seconds, reserves up to two minutes of its 15-minute start-to-close budget for cleanup, and uses `WAIT_CANCELLATION_COMPLETED` so workflow cancellation does not report completion before the physical command/provider fence has run.

| Kind              | Checks passed? | Infra error? | Outcome                                                                                                                                                      |
| ----------------- | -------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `setup_append`    | yes            | no           | `merged` — a new version is minted from the base version with the command appended to `setupScript`, and activated automatically. No `rigs:manage` involved. |
| `definition_edit` | yes            | no           | `proposed` (verification recorded, `verification.passed = true`) — awaits an explicit `rigs:manage` promote.                                                 |
| either            | no             | no           | `rejected`.                                                                                                                                                  |
| either            | —              | yes          | `failed` (retryable — establishing the sandbox, running a command, or persisting state threw).                                                               |

A `definition_edit` promote (`POST .../changes/:changeId/promote`) re-validates that the change is `proposed` with `verification.passed === true` before minting the new version from the change's base version plus its payload overrides (fields the payload omits inherit from the base). Both promotion paths (`setup_append` auto-merge and `definition_edit` explicit promote) mint the new version with `activate: true` in the same call, so a sandbox environment never has a moment with zero active versions.

Provider images are not workspace archives or restore points. They contain only the clean verified base filesystem plus sandbox environment setup, are selected only for fresh provider creation, and never carry repository contents, session resources, credentials, variable-set values, archives, session state, or processes. Existing lease recovery, archive capture/hydration, warm resume, selfhosted routing, and reaper ownership remain separate and authoritative.

Sandbox Environment audit events (`rig.change.proposed`, `rig.verification.started`/`.passed`/`.failed`, `rig.change.merged`/`.rejected`/`.failed`, `rig.version.activated`/`.promoted`) are recorded through the standard workspace audit log for every step above.

### Operational rollout

Lease-aware sandbox environment verification and destructive Modal orphan revalidation are one rollout contract, but the verifier is intentionally activated separately:

1. Pause sandbox environment-verification dispatch. Deploy the worker revision containing canonical verifier leases and the Modal orphan sweep's immediate pre-terminate durable re-read, with `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED=false`.
2. Prove every worker consuming the shared reaper/sandbox environment-verification queues is on that revision. Then enable `OPENGENI_RIG_VERIFICATION_LEASE_OWNERSHIP_ENABLED=true` as a separate configuration change and resume dispatch.

Rollback is the reverse safety order: disable the flag first, drain/stop verifier dispatch, wait until no active verifier lease remains, and only then roll the worker back. A mixed fleet must never create owned verifier boxes that an older orphan reaper cannot recognize. Disabling the flag never falls back to the legacy unleased path.

## Composition with variable sets

A sandbox environment's `defaultVariableSetIds` reference scoped Variable Sets visible to the initiating subject from the sandbox environment's workspace. Changing that field, including clearing it, requires `variable-sets:attach`; a non-empty value additionally requires `variable-sets:use` and validates every reference at sandbox environment create/edit/change-propose time. Organization- and user-scoped sets may originate in another workspace in the same organization when their scoped authority makes them visible; unknown, inaccessible, workspace-scoped foreign, and cross-organization ids remain indistinguishable and 422. Binding any Sandbox Environment version with defaults to a session independently re-requires both permissions and revalidates each referenced set for the initiating subject, including when the Sandbox Environment came from the workspace default or a post-start restart. They are pure references: a Sandbox Environment never stores variable values itself, and deleting a Variable Set that a Sandbox Environment still references is unaffected by the Sandbox Environment (Variable Set deletion semantics are governed entirely by [`variable-sets.md`](variable-sets.md#deletion-semantics), not by Sandbox Environment references). At runtime the Sandbox Environment's default sets are decrypted and merged in listed order, then the session's ordered explicit sets are layered on top in listed order — see [Default variable sets](#default-variable-sets) above.

## MCP surface

The first-party MCP server exposes sandbox environment tools, gated by the same permissions as the REST routes and **registered only for grants that hold them**:

- `rig_list` (`rigs:use`) — workspace sandbox environments and their active versions.
- `rig_get` (`rigs:use`) — one sandbox environment with one bounded active definition plus
  compact-by-query historical version/change summaries. The complete
  pretty-printed MCP result is capped at 64 KiB. Historical setup scripts,
  check bodies, change payloads, and verification logs are not copied into
  model context; totals, counts, byte facts, previews, and truncation facts make
  the omission explicit. `versionLimit` and `changeLimit` independently bound
  the two histories (default 20, maximum 100). The access-controlled REST
  version/change detail routes above remain the exact retained-detail surface.
- `rig_propose_change` (`rigs:use`) — propose an additive `setup_append` change (the exact command that already worked in this sandbox) and start verification. On a session-scoped call this attributes the change to `session:<sessionId>` rather than the caller's user subject.
- `rig_verify` (`rigs:use`) — trigger verification: pass `changeId` to (re-)verify a proposed change, or omit it to re-verify the active version's checks.
- `rig_promote` (`rigs:manage`) — promote a verified `definition_edit` change to a new active version. **Not registered for a default sandboxed-agent session**: the worker's default first-party delegated token carries `rigs:use` but not `rigs:manage`, so an agent can propose and get changes verified but cannot itself promote a `definition_edit`. An explicitly scoped owner session may carry `rigs:manage`. A `setup_append` change needs no promote tool at all: a green clean-replay run merges it automatically.

## Deletion and rollback semantics

- **Delete.** `DELETE .../rigs/:rigId` 409s while any session still references the sandbox environment (`sessions.rig_id`); there is no cascade-detach — retire or wait out the referencing sessions first, then delete.
- **Rollback.** There is no "revert" operation distinct from activation: `POST .../versions/:versionId/activate` flips the active flag to any existing version (older or newer) without minting new content or touching version rows. A rollback is exactly that call against an older version id.
- **A session's binding never moves.** Activating a different version — whether via rollback or a fresh promote — changes what _new_ sessions and re-verification see as "the active version"; it never migrates an already-bound session's frozen `rig_version_id`. A session that wants the newer (or rolled-back) version must be recreated.
