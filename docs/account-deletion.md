# Self-service account deletion

The hosted app offers **Settings → Security → Delete account**. Native clients use the same human-only API. Account deletion is permanent; it is not a request for support and is not a sign-out-only action.

## Client contract

Both routes accept the selected managed browser session or a native app session bearer (`ogapp_…`). They do not accept API keys or workspace/service credentials. Browser writes use the same origin, actor epoch and session-set CSRF checks as sign-in method changes.

| Route | Contract |
| --- | --- |
| `GET /v1/me/account-deletion` | `200` with `closeOrganizations: { organizationId, name }[]`, `leaveOrganizations: { organizationId, name, retention: { mode: "retain" \| "delete_after", days: number \| null } }[]`, `blockers: { code: "LAST_ORGANIZATION_OWNER", organizationId, name }[]` and `request: AccountDeletionRequest \| null`. |
| `POST /v1/me/account-deletion` | Send `{ "confirm": "DELETE", "operationId": "<uuid>" }`. `202` with `{ request: AccountDeletionRequest }`. |

A receipt contains `id`, `operationId`, `status` (`pending`, `running`, `blocked` or `completed`), `requestedAt` and `completedAt` (nullable). Treat the `202` as admission, not completion. The operation ID must be reused when retrying the same request. The database returns the same receipt to a retry already admitted with the same session and operation, but a revoked session cannot authenticate a fresh HTTP request. Keep an uncertain or lost response distinct from confirmed acceptance.

A `409` with `error.details.code: "LAST_ORGANIZATION_OWNER"` and `error.details.blockers` means another non-revoked member remains and there is no other active owner; transfer ownership first. No memberships or sign-ins change on refusal. `ACCOUNT_DELETION_BUSY` is a retryable `409`. Invalid confirmation is `400`, invalid or revoked credentials are `401`, browser CSRF refusals are `403`, and unavailable deletion is `503` (`ACCOUNT_DELETION_UNAVAILABLE`).

Use this timeline: “You’ll be signed out on all devices immediately. Deletion usually takes a few minutes and can take up to 30 days. We’ll email you when it’s complete.” Accounts created with a passkey and no email address cannot receive email; the hosted flow says so before confirmation.

## Erasure and retention

The admission transaction serializes against membership changes, self-offboards the person through the standard membership lifecycle, revokes their managed sessions and personal API keys, and durably stores a deletion request. A sole-member organization closes: its schedules and event triggers stop, and its shared workspaces and personal workspaces still retained for former members are erased. In a surviving organization, the organization remains the controller of its workspace data and its personal-workspace retention policy still applies. A scheduled personal-workspace erasure follows the organization's deadline, which can be later than the account-erasure window. Billing records required by law can remain; the closed organization's Stripe customer is removed, and auto top-up is turned off.

The request row doubles as a dispatch outbox. API replicas reconcile unfinished rows with the same deterministic Temporal workflow ID, including rows previously dispatched whose workflow no longer exists. Temporal invokes a bounded cleanup step with a request-specific ticket; email addresses and object keys stay out of its history. Storage erasure checkpoints are idempotent. Exact membership cleanup uses the existing claim, finalize, storage receipts and completion steps; it does not sweep other members in surviving organizations. Identity erasure keeps only revoked, de-identified stubs needed by restrictive audit and recovery references. Sign-in methods and passkeys are removed, and linked Apple credentials are revoked before their local token records disappear. Apple relay addresses receive confirmation once data erasure finishes, before Apple disconnects the address and Opengeni removes the remaining sign-in records. The confirmation address is cleared from the request after successful delivery.

The file policy only honors the deletion inventory workspace when running as the migration owner. The owner routine sets that scope after validating the exact retention claim or the closing organization and workspace; the runtime role cannot use the setting to read a private file.

## Deployment and operations

Use the normal [rolling expand/contract release](migrations-expand-contract.md). The first release adds the table and knows the two definer signatures, but withholds their execution grants. Do not grant during that migration: the still-serving previous release rejects unknown runtime-callable definers. After the deployed previous API and worker both recognize the signatures, ship a second rolling migration granting only `EXECUTE` on `opengeni_private.account_deletion_user_v1(text, jsonb)` and `opengeni_private.account_deletion_work_v1(text, jsonb)` to the runtime role, using the repository's role-grant conventions. Until then the API deliberately returns `503` and no request is accepted. Neither deployment changes existing retention deadlines or erases existing data: the new editable-document erasure path requires an explicit account-deletion request. Keep the version of the operator retention script matched to the database schema so it understands all storage obligation types. The activation deployment needs configured Temporal, managed email, and any storage, Site SQL, Stripe or Apple credentials already used by the deployment; do not add a manual production grant or a sweeper cron.

The `opengeni_account_deletion_requests` gauge reports blocked, terminal, stalled and overdue requests. `OpenGeniAccountDeletionBlocked` alerts on terminal failures, no progress for 24 hours, or requests that have not completed within 30 days. The request's `blocked_step` and `blocked_reason` identify the phase and why it stopped. Transient failures retry against the same request. For terminal failures, fix the dependency, then run `bun scripts/retry-account-deletion.ts <request-id>` with the normal runtime database role; do not edit the request. Closure cancels remaining session trees and waits for the normal workspace-deletion gates to clear. Stripe mappings in an unconfigured mode block closure rather than being dropped. Where the deployment has used both modes, configure `OPENGENI_STRIPE_ACCOUNT_DELETION_OTHER_MODE_SECRET_KEY` for the opposite mode so legacy mappings and customers found by metadata on either side can be erased. A recorded Site SQL database remains an open obligation until its configured gateway confirms erasure. This applies to account deletion and the operator retention sweep; workspaces with no such database do not need the gateway. Older sweepers cannot acknowledge a Site SQL obligation. Check that the same request advances to `completed` and that confirmation was sent. A completed request can still have targeted work pending under a surviving organization's retention policy.
