# Stripe subscription operation receipts

The subscription mutation endpoints retain the existing request/response contracts. `upgrade`, `change` and `cancel` now bind each organization-scoped request UUID to its action, requested plan, original Stripe subscription, frozen provider parameters and final result. Reusing a UUID for different action/plan parameters returns 409. Completed retries return the original result without resolving the current subscription or catalog again.

`billing-subscription-store.ts` requires a root database handle. Phase one commits the immutable intent under the organization advisory fence. A separate organization-fenced transaction performs/reconciles Stripe I/O and commits local synchronization plus the result. A provider success followed by a local rollback therefore cannot discard the original target. The provider metadata markers and schedule history recover successful operations after Stripe has pruned its request-key cache. Unknown transport/database failures leave the operation pending; retry the same UUID. One pending operation per organization prevents subsequent API mutations from overwriting its recovery marker. A definitive provider rejection or stale pre-mutation target completes an error receipt; a new UUID can then express a new request.

This serialization does not block invoice webhooks, top-ups, or the billing portal. External portal/operator changes are observed before applying an unfinished operation; a changed original target is not silently replaced with a new subscription. Checkout and portal session creation retain their existing contracts and provider keys; they do not mutate a subscription selected by the service.

Duplicate-subscription refunds use `InvoicePayment.status_transitions.paid_at`, falling back to `Invoice.status_transitions.paid_at`. Invoice creation is not funding authority: an earlier unpaid invoice paid after the replacement began is refunded, while genuinely paid pre-overlap history is preserved. Missing authoritative payment timestamps cause a retryable processing error. Existing charge-remaining checks and per-charge refund keys make repeated deliveries safe.

Migration `0796_billing_subscription_operations.sql` is maintenance-only because the prior binary's closed runtime readiness inventory rejects the new table/capabilities. Drain old runtimes, migrate/provision roles, and start only the matching binary. The journal is FORCE-RLS, runtime-readable, and writable only through account-scoped same-owner capabilities. No cleanup/TTL removes receipts: target/result binding must outlive Stripe's request-key retention.

Focused verification lives in `apps/api/test/billing-subscriptions.test.ts`, `apps/api/test/billing-subscriptions-review-postgres.test.ts` and `packages/db/test/billing-subscription-operations-postgres.test.ts`. PostgreSQL coverage migrates with a non-superuser owner in a non-public schema and uses the restricted runtime role. No test makes live Stripe calls.
