# Background-command visibility plans

`packages/db/test/background-command-visibility-plan.test.ts` exercises the restricted application role with 36,810 stopping commands and 20,001 sessions. It compares the historical policy with migration 1234 under forced generic and custom prepared plans, including sparse command reads. Assertions concern plan work, not machine-specific wall-clock thresholds.

Migration 0805 inlined child-session visibility checks. Migration 0827 (PR #4772) added `OFFSET 0` to prevent visible-session hash startup for small child reads; that was a performance fence, not an authorization boundary. The same mandatory per-command probe becomes costly on a large stopping backlog. Migration 1234 removes only that fence from the background-command restrictive `USING` expression. All other child policies and the command `WITH CHECK` keep their fences. The planner can choose indexed sparse probes or one hashed visibility set for a backlog.

On the homeserver fixture, custom/generic backlog reads previously made 36,810 session probes and 111,657 shared-buffer hits (200–206 ms). The candidate made one session scan and 2,894 hits (139–144 ms). Single-command reads retained one index lookup and six hits (about 0.12 ms). These isolated measurements establish the query-plan cause; they do not predict latency under concurrent incident load.

The alternative unconditional tuple `IN (SELECT ... FROM sessions)` was rejected: it forced sparse reads to scan all 20,001 sessions, adding about 28–30 ms. Preserve both backlog and sparse prepared-plan coverage when changing this policy again. Full tenant tuple matching, private owner checks and statement-local visibility remain authoritative; no cross-statement authorization cache is introduced.

The commands-only exception deliberately accepts one measured tradeoff: a generic prepared cold-session page (`workspace_id=$1 AND session_id=$2 ORDER BY started_at,id LIMIT 50`) hashes the visible sessions, increasing fixture latency from 3.52 ms to 36.57 ms and hits from 1,231 to 2,895. Custom pagination stays about 3.44 ms. The regression asserts the one returned row and bounded buffer work, and explicitly records this plan rather than pretending every sparse access stays indexed. This cost is accepted to prevent repeated per-command authorization across large backlogs; event/history and every other child policy retain migration 0827's fence.
