# Agent / automation notes (OpenGeni)

This repository is a clean TypeScript/Bun stack. The public API is session-based.

> **Start here for orientation: [`docs/architecture.md`](docs/architecture.md).** It is the canonical whole-system map — what OpenGeni is, the load-bearing invariants, the current workspace layout, the major ownership boundaries, and the _"if you're changing X, read Y first"_ routing index. Read it before navigating an unfamiliar area, and **keep it current**: if your change adds/removes/renames an app, package, example workspace, or sandbox backend; alters an architectural invariant, the data-flow, or the session/turn lifecycle; or changes which file is canonical for a change area — update `docs/architecture.md` in the _same_ change. A stale map is a bug. (This file, AGENTS.md, owns _how to run and operate_ the stack; architecture.md owns _how the system is shaped_.)

When the user says **"start the dev server"**, **"spin it up"**, or **"run the full stack"**, they mean the steps under **Full local stack**.

## Full Local Stack

The stack means everything needed to run the Hono API, React web app, Temporal worker, Postgres event store, Core NATS realtime bus, Temporal service, and configured OpenAI Agents SDK sandbox backend.

1. Start the full local stack:

   ```bash
   bun run dev
   ```

   This installs dependencies, starts the Docker infrastructure, runs migrations, builds the local sandbox image, and starts API, worker, and web processes.

Manual equivalent:

1. Install dependencies:

   ```bash
   bun install
   ```

2. Start infrastructure:

   ```bash
   docker compose up -d postgres nats temporal garage garage-init
   bun run db:migrate
   bun run db:provision-roles
   ```

3. Build the local sandbox image when using Docker sandbox:

   ```bash
   docker build -f docker/sandbox.Dockerfile -t opengeni-sandbox:local .
   ```

4. Copy `.env.example` to `.env` and configure at least:

   - `OPENGENI_DATABASE_URL`
   - `OPENGENI_NATS_URL`
   - `OPENGENI_TEMPORAL_HOST`
   - `OPENGENI_STARTUP_DEPENDENCY_RETRY_*` when dependencies need longer startup windows
   - OpenAI or Azure OpenAI credentials
   - `OPENGENI_SANDBOX_BACKEND` (see Sandbox Notes for the full backend list; `docker` is the default for local dev)
   - sandbox preparation profiles / env allowlist when needed

5. Start long-running processes in separate terminals:

   ```bash
   bun run dev:api
   bun run dev:worker:control
   bun run dev:worker:turn
   bun run dev:web
   ```

   The control and turn workers poll separate Temporal task queues; both must run
   or sessions are accepted but never execute a turn.

Default URLs:

- API: `http://127.0.0.1:8000`
- API health: `http://127.0.0.1:8000/healthz`
- Web: `http://127.0.0.1:3000`
- NATS monitor: `http://127.0.0.1:8222`
- Temporal gRPC: `127.0.0.1:7233`

`bun run dev` is per-worktree: infrastructure project = directory basename (main checkout dir `opengeni` → `opengeni-main`; override with `OPENGENI_COMPOSE_PROJECT`; derivation in `scripts/dev-stack-project.sh`), free host ports (ignore copied `.env` pins unless `OPENGENI_PIN_PORTS=1`), loopback URL rewrite including `nats://`, `.env.runtime` overlay. `OPENGENI_DEV_BACKEND=auto` uses Docker only when the daemon answers a bounded probe, otherwise native PostgreSQL/NATS/Temporal/pinned MinIO; explicit `docker` fails closed without a daemon. Native changes only a copied Docker sandbox default to `local`; explicit remote sandbox providers remain authoritative. `bun run dev:*` / `db:*` source `.env` then `.env.runtime`. `bun run dev:down` stops only the recorded backend; `bun run dev:clean` also removes that project's data, Docker sandbox image tags when applicable, and `.env.runtime`. Neither touches another worktree or unrelated Docker state. On mode-0700 sandbox mounts, native PostgreSQL uses an exact hashed `/var/tmp/opengeni-native-postgres` directory instead of loosening repository permissions. Sandbox image build skips when `OPENGENI_SANDBOX_BACKEND=none`. Docker sandbox builds remain source-correct for dirty worktrees, use worktree-specific image tags and live leases, retain a bounded recent image history, and use the fixed OpenGeni-only `opengeni-development-sandbox` BuildKit cache; the build exports into the Docker daemon only when the daemon does not already hold the exact cached result. The builder runs with one explicit BuildKit GC policy equal to the cap (encoded in its node name, so a changed cap recreates the builder once) because BuildKit's default GC prunes toward ~10% of the Docker disk whenever free space is low and would otherwise evict the cache between starts; the launcher warns when Docker's free disk cannot hold the cap. Tune its local-only bounds with `OPENGENI_DEV_SANDBOX_IMAGE_RETENTION` and `OPENGENI_DEV_SANDBOX_BUILD_CACHE_MAX` (default 24 GB; one full build keeps roughly 10-14 GB of records, and a cap below that working set makes every start rebuild; a copied pre-measurement `6gb` value is treated as unset) rather than pruning unrelated Docker images, volumes, or project caches. `OPENGENI_DEV_CARGO_TARGET_DIR` (opt-in, absolute path) lets parallel worktrees share the host-side Cargo target cache for the artifact kernel and relay builds.

Garage is the local S3-compatible object storage default for Docker Compose and optional self-contained Kubernetes smoke tests. Native development uses pinned MinIO; Docker MinIO remains an explicit opt-in (`OPENGENI_OBJECT_STORAGE_FIXTURE=minio` or Helm `minio.enabled`). Production deployments should use provider-native storage instead of deploying Garage or MinIO manually: `azure-blob` for Azure Blob, `aws-s3` for AWS S3, and `gcs` for Google Cloud Storage.

## Architecture Notes

For a map of every app, package, and how the parts fit together, start at [`docs/architecture.md`](docs/architecture.md) and follow its links to the focused topic docs.

- Public clients talk only to the API.
- Organization-tenancy Slices A+B stage the `Organization → Workspace → User`
  authority hierarchy: `managed_accounts.id` remains the physical organization
  id, organization membership is distinct from ordinary workspace membership,
  and managed-human provisioning creates one same-org personal workspace
  pointer plus its normal control row without a durable `workspace_memberships`
  row for that personal workspace. The first narrow runtime exception derives
  an owner-only personal-workspace grant only for the canonical managed-cookie
  (Better Auth) session, after the exact active organization membership and its
  personal-workspace pointer converge through the lifecycle SECURITY DEFINER
  seam. Bearer/delegated principals, API keys, and account or organization
  administrators receive no personal-workspace access through that exception.
  The exact built-in `opengeni:local/default` + `dev` browser context is also
  the sole organization administrator in single-user local mode. It may manage
  organization metadata, shared workspaces, retention, company identity, and
  the organization Codex pool; subject names alone, configured access, bearer
  tokens, API keys, services, and agents never inherit that exception.
  Because that workspace has no `workspace_memberships` row, a seam that fences
  on one denies its owner: `subjectHasLiveWorkspaceAuthorityInScope`
  (`packages/db/src/workspace-authority.ts`) is the single implementation of the
  corrected rule. **Neither that resolver nor its exported
  `namedSubjectHasLiveWorkspaceAuthority` sibling is an authorization** — both answer
  "does subject X hold authority here" and neither establishes that the caller
  is X. The exported one sets `opengeni.subject_id` from its own argument, so it
  is an arbitrary-subject oracle; never pass it a request-derived subject. The
  in-scope one refuses to set that GUC and raises when the requested subject
  differs from the transaction's scope, but that is a **consistency check, not
  an authorization**: the scope was itself set from a caller-supplied argument,
  so it catches only a caller naming a third party mid-transaction. The single
  thing that authorizes the exception is the API layer's
  `AccessGrantAuthorization.canonicalManagedHumanSession`, stamped only where a
  Better Auth cookie was verified — never a shape check on the grant
  (`principalKind`, `metadata.delegated`, `serviceInitiator`), all of which a
  delegated token chooses for itself. A new caller must get that stamp right;
  the resolvers will answer `true` for whatever subject they are given.
  The four authority/grant tables remain FORCE-RLS with zero direct app DML;
  scoped Variable Sets are the activated exception with explicit
  organization/workspace/user ownership and common personal-resource grants.
  All remaining APIs, resources, sessions, and lists remain
  workspace-owned/workspace-shared. Session visibility is now product-reachable
  for an activated organization: migration 0225 activated owner derivation, the
  capability-fenced direct-write trigger, and visibility-aware reads; 0303
  activated the first public caller; and migration 0336 makes
  `fork_session_content` an atomic, idempotency-keyed fork into either
  visibility with `replay_applied_session_fork` recovering a committed
  destination before mutable source authorization is consulted. That boundary
  is still exactly one caller wide - `packages/core/src/application/session-tenancy.ts`,
  reached only by the two HTTP routes and the SDK - and
  `test/session-visibility-contract-surface.test.ts` pins every SQL and adapter
  entry point, including the replay surface. Worker, MCP, runtime, React, and
  cross-workspace callers stay forbidden; adding one requires updating that
  test deliberately. Migration 0323 adds a separate
  owner/admin organization setting (`organization_private_session_settings`)
  that, together with the 0303 readiness receipt, gates new Only-me creates in
  shared workspaces; migration 0336 applies the same product decision to a
  private fork destination in a shared workspace, after keyed replay so a
  committed fork still replays once an owner disables the setting; and migration
  0344 gates a fresh transition to Only me while preserving the same replay and
  Personal-workspace exemption. The setting grants no access. Owner derivation reads STATED
  authority only: an active membership's own `personal_workspace_id` pointer or
  an explicit `workspace_memberships` row (migration 0302). Never widen it to a
  default workspace, `created_by`, or current access, and never let an
  unresolved owner inside an active membership's personal workspace fall back to
  a silent NULL. Do not add the first caller
  without the activation prerequisites (cache/pin stripping, cancellation,
  owner-only grants) and an update to
  `test/session-visibility-contract-surface.test.ts`. An organization-wide
  lifecycle seam serializes on the transaction-scoped advisory key
  `hashtextextended('organization-membership:<organization id>')` and may take no
  lock stronger than `managed_accounts FOR KEY SHARE` before the canonical
  workspace prefix (migration 0299): every ordinary workspace writer
  holds its `workspaces` row and then reaches `managed_accounts` through the
  account FK check of a row it inserts, so an organization-row `FOR UPDATE` held
  across workspace acquisition is a deadlock. See
  `docs/organization-tenancy.md`.
- Domain/access/billing helpers now live in `@opengeni/core` under `packages/core/src`; `apps/api` routes are HTTP adapters over them.

- Browser streaming uses `GET /v1/workspaces/:workspaceId/sessions/:id/events/stream` with SSE.

  before durable outbox acknowledgement.
- Postgres is the durable event store and replay source.
- Workspace-control events are compact invalidations, not evidence blobs: control reasons and
  actors have canonical UTF-8 ingress/storage bounds, legacy rows carry explicit loss facts, and
  REST/NATS/SSE projections are independently byte-bounded. The rolling storage migration rewrites
  only pre-existing cap violations; already-bounded legacy rows stay untouched with projection-time
  byte facts.
- Temporal is orchestration only. Token streams do not go through workflow history.
- OpenAI Agents SDK execution happens inside non-retryable worker activities.
- Agent activities are side-effectful. Do not add automatic Temporal retries around full agent turns unless each model/tool/sandbox boundary has been made idempotent.
- Live agent session authority is capability-first. An exact current agent attempt may read, message, and control peer workspace sessions; parent/child lineage is not an access deny. Slack-private stays same-root for agents, and `user_private` still requires the initiating human as owner. An agent cannot Steer itself. Goal tools stay self-only. A live attempt may answer another session's structured human-input request (`session_human_input_respond`, `session.human_input.write`) but `session.approval.write` is denied to every agent attempt: tool approvals stay human-only. Compact `sessions_list` discovery still validates the live attempt. An optional embedding-host callback may narrow access; it cannot grant a private session OpenGeni denied. See `docs/agent-session-authority.md`.

Apply tenancy/private-session rules, exact attempt validation, Slack-private scope, and optional host list narrowing before lifecycle filters, title/active-goal/typed-claim matching, ranking, counts, cursors, or ancestor expansion. Never search `initialMessage`, instructions, resources, tools, files, or full history. Work claims are bounded, durable, non-exclusive evidence with exact-attempt CAS/idempotency and lifecycle settlement; they do not lock, reserve, reassign, authorize, cancel, steer, message, or require a search. Preserve the literal `advisoryOnly` and `noAdditionalAccess` projection facts, keep automatic nudges off until separately reviewed, and use the independent rollout switches instead of deleting evidence or rolling back migrations. See `docs/work-discovery.md`.
- Codex rate-limit reset credits are never automatic agent capacity. Their
  irreversible consume path is managed-cookie owning-human web-only with durable
  provider idempotency; do not add an SDK, MCP, Codemode, worker, scheduled, or
  allocator/rotation consume hook. See `docs/codex-subscription-rotation.md`.

## Run Lifecycle (read `docs/run-lifecycle.md` before changing the session workflow, the agent turn activity, or memory)

Three principles here are load-bearing and easy to break by accident:

- **No default run-length limits, by design.** OpenGeni runs agents that legitimately work for days. Budget/admission policy and explicit goal completion or pause bound execution; OpenGeni does not infer "no progress" from tool/event shape. Do not add or lower caps on model calls per turn, continuation count, or activity timeout as a way to "be safe" — fix the pathology instead. See `docs/run-lifecycle.md` and `docs/goals.md`.
- **Three memory stores, three jobs.** `session_history_items` is protocol-preserving, exact JSON conversation truth fed to the model (default read path); SDK-origin history, pending tool call/result receipts, approval snapshots, and durable event projections pass through one protocol boundary that omits only object properties whose JavaScript value is `undefined` (JSON-wire absence) and rejects every other non-JSON graph with a path. Accepted user, agent, tool, and source content is never regex-scanned or rewritten because it resembles a credential. `session_pending_tool_calls` holds in-flight receipts plus the bounded `requires_action` open suffix (pending call, tied reasoning, interruption kind); unpaired calls never enter model-facing history. `agent_run_states` holds the open-suffix sentinel plus approval/human-input control snapshots and is never conversation memory — resume uses the open suffix plus paired history. `session_events` is the exact append-only human/audit timeline for accepted payloads and must never be fed back to the model; deterministic size/protocol projections are separate from content classification. Sandbox recovery state is separate again in `sandbox_session_envelopes`. Workspace Memory (`knowledge_memories`) is retrieval context, never conversation memory: when `memoryEnabled` is true, exact live agent attempts autonomously save and correct active facts, decisions, incidents, fixes, and outcomes through `memory_save` / `memory_correct`, independent of Learning mode, while the curated docs-MCP Knowledge lane remains human-reviewed. Accepted memory text is stored exactly. Its typed workspace/user/role/session/ephemeral selectors are enforced by FORCE RLS; missing context denies, relationship reads require both endpoints, and lifecycle evidence is immutable, exact-actor, and value-free. Scoped knowledge provenance (`knowledge_providers` through immutable claims/evidence/reviews) is separate again: it is RAG evidence rather than prompt state or active memory, uses exactly organization/workspace/initiating-user authority, and proposal rows never activate policy or preferences. Instruction-policy onboarding proposals likewise create only immutable evidence plus an inactive revision in the existing policy authority; they never become a parallel prompt/memory store or activate policy themselves. The human-confirmed `remember lane=knowledge` path remains only as a reviewed fallback when autonomous Memory is unavailable: its confirmation-to-Memory receipt preserves exact approved text in a receipt-specific namespace, cannot dedupe to a normalized lookalike, and replays the same Memory id after archival. Workspace learning policy is another separate authority: immutable `off`/`suggest`/`automatic` revisions plus sparse source overrides resolve only from an accepted-attempt snapshot, never directly from a mutable head; it does not gate autonomous Memory and authorizes no destination write by itself. Do not infer human authority from session creation or provenance metadata, expose legacy scopes to the runtime role, mutate typed selectors/edges outside the lifecycle functions, or bypass learning-policy activation/rollback with direct head/event writes. See `docs/hierarchical-memory.md`, `docs/scoped-knowledge.md`, `docs/workspace-instruction-policies.md`, and `docs/workspace-learning-policy.md`.
- **Agent-authored durable text is prompt cost and is bounded by where it lands.** A mandatory workspace rule is composed verbatim into the prompt of every session it applies to (every session for a global charter/policy, every session bound to the role for a role policy; at most three entries compose at once), so **every** agent surface that reaches that destination is capped at `AGENT_AUTHORED_INSTRUCTION_POLICY_CONTENT_MAX_CHARS` (600): `remember` lane `instruction_policy`, `instruction_policy_propose`, **and** `task_note_promote_instruction_policy`. The preference destination is capped at `AGENT_AUTHORED_PREFERENCE_CONTENT_MAX_CHARS` (1,200) across `remember`, `preference_propose`, and `task_note_promote_preference` - not because its content is composed (only its short descriptor is; the content is retrieved on demand) but because that length is retrieval cost. The Knowledge lane keeps `REMEMBER_CONTENT_MAX_CHARS` (4,000). Organization identity and mission are capped for agents at 400 characters each through `AgentAuthoredCompanyProfileContent`; historical list bounds remain only so stored revisions validate. The budget follows the **destination**, so a task note (bounded only by `TASK_NOTE_TEXT_MAX_BYTES`) must never become a way around it: promotion is checked in `packages/db/src/company-brain-governed-writes.ts` and rejected, never truncated, before any evidence/claim/proposal row is written, while the note bytes stay exact evidence. Human API limits and stored revisions are deliberately unchanged. The `remember` confirmation card names the character count and destination on the question `label` - never on `prompt`/`helpText`/`options`, which migrations 0272/0274/0284/0293/0316 byte-verify. See `docs/company-brain-write-routing.md`, `docs/workspace-instruction-policies.md`, and `docs/company-profile.md`.
- **Organization identity is its own bounded organization authority.** `company_profile_revisions` plus one active head and immutable activation events own concise identity and mission. The storage/API contract retains products, customers, goals, and constraints arrays only for historical revision/hash compatibility; current UI and agent proposals leave them empty. Nonempty lists on an already-active historical revision remain prompt-composed as explicitly labeled compatibility context until an organization owner replaces that profile, preventing silent context loss while those facts move into organization-scoped Documents/RAG. New or changing organization facts are retrieved only when relevant. Head/event mutation is lifecycle-only through the tenant/actor/CAS-fenced function; runtime access to those tables is read-only. Exact accepted attempts freeze the authority in `company_profile_snapshots`, and the existing workspace-governance composer places identity/mission plus any retained compatibility entries after CORE and before workspace charter/policy. A snapshot containing only retired nonempty list fields remains prompt authority until replacement. The workspace `memoryPromptMode` is always `retrieval_only` and omits the entire profile from child prompt composition while preserving the frozen snapshot and root composition; it never weakens instruction policy or descriptor catalogs. Organization mutation requires exact account authority (`account:admin`, held by organization owners). Explicit agent administration uses the first-party `company_profile_propose` tool only from an exact live turn initiated by the current active owner. Its separate organization-owner policy defaults to `suggest`: `off` creates no proposal, `suggest` stages an inactive identity/mission revision and binds one structured-human confirmation before `company_profile_confirm` can activate it, and `automatic` activates the same proposal through the existing CAS lifecycle without another prompt while retaining the causal owner and frozen policy version in immutable receipts. Workspace learning mode and workspace-admin authority never govern or widen this path; the agent never receives `account:admin`, and automatic activation uses the truthful `service:company-profile-autonomy` event actor. Migration 0360 preserves rolling safety by including any legacy list content submitted by an older API instance in a bound Review-first confirmation. Historical durable-learning list subjects remain compatibility-only and are not permission for new standing fields; new non-identity facts route to organization knowledge. See `docs/company-profile.md`.
- **Exact content and configured-secret authority are separate concerns.** Never add a central heuristic/exact-value redactor to model context, history, events, memory, tool calls/results, failures, diagnostics, transcription, or UI data. Configured secrets remain authenticated-encrypted at rest. Plaintext list/read/write is an explicit permissioned operation (`secrets:list|read|write` and `variable-sets:list|read|write|attach|use`), tenant/session constrained and metadata-only audited; audit rows never contain the value. Masking is allowed only at a genuinely public or third-party sink and must not mutate OpenGeni's stored or agent-visible data. Historical bytes already rewritten by older releases are irrecoverable.
- **Goals drive long runs through a Postgres obligation, not workflow polling.** Terminal settlement atomically advances an active goal's monotonic wake revision and the workflow-wake outbox; one transaction materializes that revision as the typed update, events, usage fact, observed revision, session transition, and successor wake. Human/Steer work, approval, recovery, provider waits, recursive Pause, and cancellation remain authoritative. Temporal signals/runs are repairable nudges only. The exact accepted-turn goal snapshot is appended only to that turn's newest durable model-input item: the human/API user message, or the canonical user-role continuation message for a goal-owned turn. Other coalesced machine updates remain attached as message context. An agent-declared `goal_wait` hold never consumes the wake revision: the materializer returns `held`, re-arms a delayed outbox wake at the deadline on every idle evaluation, and pending `immediate`-class machine input still wins with `queue` (a `deferred` child lifecycle notice leaves a current hold in place and is delivered when it ends); any newer finished turn, a passed deadline, or a human/API/agent goal mutation clears the hold. Never move this authority to `Agent.instructions` or ephemeral worker context; preserve append-only prompt-cache prefixes and exact recovery. `auto_continuations` counts only consecutive synthesized continuations that consumed no external input (the claim binding a goal turn to a batch with any other machine input resets it), consecutive no-input continuations are paced by a delayed workflow-wake row (`goal_idle_backoff`, default 3 s/30 s/2 m/5 m, never a Temporal timer or a cap), a hold whose deadline has just passed is due now (that evaluation skips the backoff once), and a `max_auto_continuations` pause is pacing rather than intent: every external input producer (child results, scheduled occurrences, media results, Agent messages, Agent Steer, human/API Send/Steer) auto-resumes it in the same commit with `goal.resumed{reason:"external_input"}`, while `user_pause`/`api`/`agent`/`limits` pauses are never auto-resumed and the agent-facing `goal_set` no longer accepts `maxAutoContinuations`. See `docs/goals.md`.
- **Governed goal revisions and root constraints activate at maintenance migration 0257.** Stop every old API, control-worker, and turn-worker before applying `0257_goal_revision_decisions_and_root_constraints.sql`; supply the exact old/new runtime login list through `OPENGENI_MIGRATION_APPLICATION_DATABASE_ROLES` (or `applicationDatabaseRoles` for programmatic/dedicated-schema migration). A live listed identity aborts activation with SQLSTATE `55000`. After it commits, never restart a pre-0257 image: old workers strip the accepted-turn root-constraint authority. Preserve the existing raw-array goal-revision list; bounded pagination is the separate `/goal/revisions/page` contract. See `docs/goals.md`.
- **Synthesized follow-up turns preserve the effective model policy.** Goal continuations inherit model + reasoning + latency mode from the newest turn that durably emitted `turn.started`, falling back to the session default only when no turn has actually run. Agent-spawned children inherit omitted model + reasoning + latency fields from the exact worker-signed calling turn; explicit child values still win. A claimed turn rejected during admission must not silently switch the next turn's provider or billing owner. Child terminal results always enter the bounded typed internal-update batch for their parent.
- **Context compaction is one durable transition, mode-frozen per session.** Non-Codex sessions and Codex sessions frozen `portable` use Codex's local plaintext checkpoint: the summarizer sees a protocol-valid temporary copy of active structured history plus the fixed checkpoint prompt; the replacement is newest real user messages in one cumulative 20,000-token budget plus one summary. Codex sessions frozen `remote_v2` (default for new Codex sessions; workspace may opt into `codexCompactionDefault: "portable"`) call Codex remote compaction v2 (`compaction_trigger` + beta `remote_compaction_v2`), persist the opaque `{ type: "compaction", encrypted_content }` item with retained user/developer messages including images (64k budget). The compact request must reuse the ordinary turn prompt-cache prefix (exact agent instructions + model-visible tool schemas; empty instructions rejected; operator `/compact` on `remote_v2` builds the agent first), and admit only Codex models for the session lifetime — fail closed with no portable fallback. Mode is written once at create; existing sessions backfill `portable`. Shared Slack authority is exclusively the OpenGeni workspace bot (`app_install`), whose bot token now carries `search:read.public|files|users`; never reintroduce a workspace-owned `slack.com`/`oauth2` proxy identity. See `docs/slack-bot.md`. A personal connection becomes executable only through the exact immutable delegation snapshot frozen on the causal turn or scheduled task. Direct Send/Steer snapshot the authenticated subject's selected active rows; children copy the spawning `parent_turn_id`; goal continuations copy the latest finished causal turn; accepted schedule occurrences copy the task snapshot; ordinary internal updates coalesce only when their snapshots match. Recovery and approval retain the same turn snapshot. At execution, revalidate exact workspace membership plus connection id/provider/kind/owner/status; if unavailable, omit only that MCP and emit the visible personal-authority warning instead of borrowing another subject's row or aborting unrelated work. Workspace-owned connections take the same accepted-use authority (migration 0279): every credential resolution and provider request revalidates the exact live workspace row - same lifecycle fences, same idempotent audit facts - and a frozen personal snapshot for the same turn+server denies a workspace-scope borrow outright; only a pre-snapshot ref with no connection id keeps the bounded unprivileged legacy resolution. Public queue/turn/task projections expose only `{serverId, providerDomain}`, never connection UUIDs or owner subject ids. Gmail's REST bridge is transport substitution, not new authority: it is the unconditional sole execution path for the official-Gmail connection (never a passthrough to Google's Developer Preview MCP endpoint), and it may resolve its credential only for the canonical Gmail `users/me` REST subtree. Google Drive publication freezes its exact output destination on the accepted delegation and fails closed on live drift; every publication sits behind exactly one durable execute-once connector fence - the attempt connector-action wrapper for model callers, the tool's own registration for Codemode callers (never both: a second registration would mint a duplicate ledger row and deadlock the ask policy) - settling `not_executed` (retry-safe) before the first mutating provider request and `uncertain` (outcome unknown, never blind-retried) after it.
- **Slack workspace routing splits home from target tenancy.** Home is the installation binding: the bot credential and connection, the post/update/delete ledgers, the inbox rows, `slack_bot_user_links` identity, App Home, reaction-summon settings, Slack task policy, and the route/prompt tables. Target is the routed workspace: the `slack_interactions` row, its action handles, progress deliveries, shared-task origins, the grant, the session, and every session event. Every bot client is built from home: the interaction edge fails permanently when the installation binding no longer names its exact connection, while delivery and shared-result publication instead fall back to the interaction's own tenancy (the pre-routing behaviour, still fenced because the post ledger claims the connection under the tenancy it was given). The read-only bot tools frozen on a Slack-origin session are the one genuine exception, running under the session's grant and so resolving a target-workspace connection. A routed workspace never falls back to the installation's when the subject lacks access and no session is created, but only an ordinary Slack message (mention, command, DM, shortcut, thread reply) ever offers the access-request link, and only for a resolved route other than the installation's own workspace or a mapped thread, whose authority then failed; an unreachable or ambiguous prefix, an empty candidate list, and a refused picker answer are all refused without one, while a lost mapped thread, any route while the flag is off, any resolved route whose live grant lacks `sessions:create`, and a reaction summon whose resolved route fails authority all fail silently and permanently. Enabling the flag is therefore a visible change: the resolver stops short-circuiting to the installation, so a single-workspace install resolves a sole candidate and posts a refusal where the old code was silent. The identity link itself stays home. Routing is decided from durable facts before any agent runs, so it is never a model judgement, and it is same-organization only by table CHECK. Both content-free tenancy probes are organization-fenced, and neither leans on `SECURITY DEFINER`, which does not escape FORCE RLS under a non-superuser owner. They escape it differently: the interaction probe opens its own row through the 0243 private transaction-capability pattern, while the action-handle probe reads a private trigger-maintained ids-only mirror instead, because that table's RESTRICTIVE visibility policy cannot be opened by a permissive one. A channel never counts a personal workspace as a routing candidate: it is the wrong destination for a shared thread, and because every managed member is provisioned one, counting it would mean nobody ever had exactly one candidate and a single-shared-workspace organization would be asked to choose in every channel. A bot DM still resolves the sender's own personal workspace. The whole feature is governed by `OPENGENI_SLACK_WORKSPACE_ROUTING_ENABLED` (default **on**); setting it to `false` is now the deploy decision that restores the short-circuit. See `docs/slack-bot.md`.
- **Delegated service provenance never replaces authorization.** A trusted embedding host may sign a service-only causal initiator separately from the delegated grant subject. The grant subject and permissions remain the access boundary; the service assertion is immutable provenance only, cannot impersonate a human, and cannot coexist with exact worker-signed agent-attempt claims.
- **Goal mutations and their timeline facts are one session-sequenced commit.** Agent/API set, update, complete, pause, resume, and clear use the canonical event-write prefix—`workspace_inference_controls FOR SHARE` when control-aware, then the actual `workspaces` row `FOR KEY SHARE`, then the session `FOR NO KEY UPDATE`—before mutating the goal and appending its event in that transaction. Agent `goal_update` additionally requires one target-scoped operation receipt that atomically stores its exact result and remains replayable across replacement attempts without overwriting a newer revision. Never mutate a goal and append/publish its event in separate commits, and never take an unnecessary workspace `FOR UPDATE` solely around a goal event: both patterns can recreate the active-turn/goal-tool self-lock.
- **Temporal cancellation is not physical quiescence.** Receipt-gated v2 workflow histories first close and fence the exact attempt in Postgres, then request nonblocking Temporal cancellation. The exact `runAgentTurn` activity owns the hard sandbox/tool fence, including draining sandbox/tool operations plus attempt-owned Git, Codemode, and generic run-credential renewal/materialization writes, and normally writes `quiesced_at` immediately after they drain; that receipt, its queue event/session revision, and the exact workflow wake commit atomically. If all three direct receipt transactions fail, the same activity retries delivery of one immutable account/workspace/session/attempt/workflow-run/activity proof through `signalWithStart` (bounded delivery backoff, no DB re-evaluation). The workflow must persist every accepted proof before peeking, closing, or continuing as new through its DB-only control activity with unbounded Temporal retry. If the activity process disappears after logical interruption, `cancellation-wait` may recover the same receipt only after Temporal proves the exact persisted workflow-run/activity identity is absent or its server-owned heartbeat lease expired **and** the complete durable writer set is closed: the attempt is closed, its interruption is settled, and every turn admission, retained process, and retained-process child admission is physically settled. The heartbeat lease proves only that the activity owner vanished; it never substitutes for provider-operation exit/loss proof or writer settlement. Arbitrary age, workflow closure, holder expiry, or a merely requested cancellation remains insufficient. The existing Postgres receipt transaction remains the only authority that can set `quiesced_at` or open admission. NATS publication is live fanout only and neither creates nor substitutes for the receipt. Attempt-qualified credential-generation deletion plus provider/batcher/lease/cache/recording cleanup after the fence is detachable and cannot erase successor state. Until the receipt exists, every claimer stays blocked even if the Temporal activity completed or failed; the workflow may close after a bounded `cancellation-wait` and is restarted by the proof signal or wake outbox without a quiescence scanner, polling loop, synthetic prompt, effect replay, or duplicate visible work. Queue stopping telemetry is scoped to the latest attempt and may be true with an empty visible queue. Keep heartbeat cancellation delivery throttled to five seconds. Histories without the `session-attempt-quiescence-v2` patch retain the v1 WAIT/fallback command order only for deterministic replay; new histories must never take that path, and it may be removed only after those runs drain.
- **Durably adopted background commands are session-owned, not attempt-owned.** Adoption must commit the exact provider locator under the canonical control + exact-attempt fence before a live command ID is returned. During Connected Machine adoption, the op-stream yield path temporarily owns exact failure cancellation so Steer cannot cancel after the transfer begins and a rejected adoption still exact-cancels. Normal turn completion and Steer detach without cancellation. Session/workspace Pause and terminal Cancel atomically move matching commands to `stopping`; Resume never revives them. Managed commands retain their exact process holder and sandbox, while Connected Machine commands retain the physical control workspace, enrollment, connection instance, and op ID. Session/workspace deletion blocks on active command authority; successful source-workspace deletion alone prunes settled cross-workspace origin history. Reconciliation accepts only typed terminal provider proof, checkpoints it before settlement, and never rebinds to a successor or infers death from age/offline state.
- **Stream cancellation must not accumulate losing promise reactions.** Temporal's `Context.cancelled` intentionally never settles when an activity completes normally. A long token/event loop must therefore await its iterator through `Context.cancellationSignal` with a listener removed after each successful read; never `Promise.race` every event against the lifetime cancellation promise. Preserve the exact cancellation reason and one-pending-read behavior.
- **Accepted direction wake delivery is admission-aware.** Temporal accepting `queueChanged` or `sessionControl` is transport evidence, not proof that a closing or continuing workflow observed Postgres. While effective control is active, the current coalesced wake revision remains unacknowledged while an accepted human/API turn is still queued, and any wake remains unacknowledged while an `agent_steer_instruction` is pending; the bounded dispatcher keeps retrying until the attempt-fenced claim adopts each direction exactly once. An older acknowledgement may advance only its own revision and cannot hide newer queued work. Duplicate signals remain wake hints and cannot duplicate inference. A real Pause is a truthful admission blocker and may acknowledge the old revision; Resume must commit a fresh wake revision for the still-pending direction.
- **Historical interruptions never become new control signals.** Wake repair emits `sessionControl` only for an undelivered control revision, an actionable interruption, or a settled interruption whose exact attempt still lacks physical quiescence. A fully quiesced historical Pause/Steer row is audit evidence only; it must never upgrade a later ordinary queue wake or cancel an unrelated live attempt.

The agent turn implementation and Temporal activity identifier are both
`runAgentTurn`; session control uses the `sessionControl` signal. The production
cutover drains and terminates every old session workflow before the new worker
starts, so no removed activity/signal identifier or replay adapter belongs in
the new runtime.

## Pull-request delivery across moving `main`

Treat a candidate as an immutable semantic source revision, not as a snapshot of
the latest protected branch. Create the branch from current `main` initially,
then keep the exact head frozen while CI and review run. Ordinary PRs into
`main` use focused impact CI; freeze-head source admission runs only for
`hotfix/*` PRs into `production`.

- A protected-branch advance alone is **not** a source revision, does not
  invalidate a head-bound review, and must not produce another candidate label.
  “Current-main compatible” means that the frozen head's patch and
  resulting merge tree have been checked against current `main`; it does not
  mean that current `main` must be an ancestor of the candidate head.
- When `main` moves, leave the source branch untouched. Inspect provider
  mergeability and have the merge authority prove the fresh latest-main
  conflict, patch-equivalence, protected-path, migration/generated-file, and
  targeted compatibility checks. Do not merge or rebase unrelated `main`
  commits into the branch solely to make it look current.
- Mutate the candidate only for a source defect, an actual merge conflict, or a
  material semantic incompatibility that requires source changes. Record that
  reason explicitly.
- A structured release-review artifact that explicitly binds a reviewed base
  may need replacement evidence when that selected base identity changes. That
  evidence refresh stays on the same candidate head.
- Watchers and continuation goals must say “verify compatibility without source
  mutation.” They must never direct a source owner to “reconcile again” merely
  because `main` advanced. Candidate/version numbers count substantive source
  changes only.
- Run independent review as soon as the candidate is ready; CI and review may
  proceed concurrently, while merge still waits for both.

Promote `main` → `production` with a merge-commit PR (never squash / never
GitHub rebase-and-merge). Hotfix PRs into `production` keep freeze-head
admission; see `CONTRIBUTING.md` § Release / Publishing.

See the hotfix admission contract in
`.github/workflows/source-admission.yml`, `scripts/check-source-admission.mjs`,
and `scripts/check-source-admission.test.ts`. Do not reintroduce an
exact-current-tip ancestry requirement in prompts, goals, documentation, or
operator procedure.

## Sandbox Notes

Sandbox execution is pluggable. `OPENGENI_SANDBOX_BACKEND` selects one of the backends defined by the `SandboxBackend` enum in `packages/contracts/src/index.ts` (the canonical list): `docker`, `modal`, `local`, `none`, `daytona`, `runloop`, `e2b`, `blaxel`, `cloudflare`, `vercel`, `selfhosted`, and `opensandbox`. `docker` is the default and the usual local-dev choice; `modal`, `opensandbox`, and the other cloud backends are provisioned, swappable boxes. OpenSandbox is optional and Kubernetes-native: exact attach is by persisted ID, workspace recovery uses OpenGeni portable tar archives in object storage (required; never silent jsonb stuffing), provider TTL is renewable, and a desktop-class image reports ttyd PTY plus desktop/recording over signed URI-mode ingress when `OPENGENI_OPENSANDBOX_SIGNED_ENDPOINTS=true` (unsigned keeps the lifecycle proxy); native snapshots and `runAs` stay unavailable. When you change the set of backends, update the enum first and treat it as the source of truth — this file and the README follow it.

There are two stock sandbox images. `docker/sandbox.Dockerfile` is the official headless release image (the 7-image BOM). `docker/desktop.Dockerfile` is the Modal Computer/Browser box (Xvfb, XFCE, Chrome, `opengeni-browserd-up`). It is **not** in the BOM and does not ride an API/worker Helm upgrade. Publish it with `.github/workflows/publish-desktop-image.yml` and pin `desktop.imageRef` / `OPENGENI_MODAL_IMAGE_REF` to that digest. Helm and production boot fail closed when Modal desktop is on without a `@sha256:` pin. Never point Modal Computer/Browser at `opengeni-sandbox`. A new pin applies to new sandbox creates only; an existing warm lease stays on the old box until rotate/reap.

The Docker sandbox image includes Terraform, Checkov, AnyDoc, Azure CLI, GitHub CLI, git, jq, curl, and base shell utilities. AnyDoc is a pinned local document-to-Markdown parser; its matching `document-parsing` guidance is opt-in and never downloads code at runtime. Managed sandboxes also provision git-provider CLI auth wrappers for `gh`, `glab`, and `az`; direct provider-token bindings read their current token files at invocation time and pass through cleanly when a token file is absent. A host-owned HTTPS smart-Git broker binding is deliberately Git-only: its bearer is never exported to a provider CLI, and the wrapper fails with guidance to use the configured provider MCP tools. Terraform, Checkov, document-parsing, social-marketing, and provider-specific guidance are immutable opt-in entries under `packages/runtime/src/curated_skill_library`; they are materialized only by an explicit Skill installation, Pack, or session selection and are never deployment-default workspace capabilities.

### Bring-your-own-compute — the Connected Machine (`selfhosted`)

A **Connected Machine** (the `selfhosted` backend) is a user's own always-on machine — a **first-class, co-equal PRIMARY compute target**, not merely a swappable sandbox. When a turn's _effective_ backend is a machine, the agent runs on it **directly**; there is no provisioned box behind it. Use "Connected Machine" in product-facing prose and reserve "selfhosted" for the enum value / internal plumbing. Key invariants — do not break them:

- **One host agent may serve many independent control planes.** A connection is identified by normalized deployment API origin + workspace id, keeps its own credentials/NATS/relay/epoch/reconnect lifecycle, and namespaces operation identity inside the shared host engine. Adding, refreshing, removing, or losing one connection must not replace, detach, cancel, or expose another; host capacity, containment, spool, and the native platform remain process-wide because they describe the one physical machine.
- **Machine-primary, not a phantom box.** A machine-targeted turn establishes the `SelfhostedSession` **directly** (`establishSelfhostedTurnSession` in `apps/worker/src/activities/agent-turn/sandbox-establish.ts`, the `machinePrimary` branch) and does **not** acquire or mutate the managed-home lease. The active-sandbox pointer supplies the machine route's epoch fence; the separate cloud lease owns only managed-box recovery, snapshots, billing, and reaping. Therefore a degraded cloud archive cannot block a healthy explicitly selected machine, and no Modal/cloud box is created, leased, or billed for that turn.
- **No durable platform credential or setup crosses to the machine.** A `selfhosted`-effective turn skips platform Git delivery and every managed-box setup hook; the machine owns its Git auth, ambient environment, and manually provisioned credentials. The sole narrow exception is exact-attempt Codemode: the worker keeps its renewable `codemode:call` bearer in memory and snapshots the URL + current bearer only into each newly launched child command. The values never enter the machine manifest, filesystem, session/RunState serialization, argv, or logs. The installed Rust agent exposes its own absolute path to that authorized child as the native no-runtime client; every call still terminates at the same public attempt journal and executor. Machine unavailability must surface through the sandbox tool result, never fail turn admission before the model runs.
- **Repos are never cloned onto a machine.** `repositoryUsesSandboxClone` (`packages/runtime/src/index.ts`) returns `false` for a `selfhosted` effective backend (the clone-guard) — the machine already owns its filesystem, so a platform `git clone` must never land on the user's real disk.
- **Per-session working directory, not a fixed `/workspace`.** A machine runs under `sessions.working_dir` (migration 0027); `toMachinePath` (`packages/runtime/src/sandbox/selfhosted/session.ts`) re-anchors the virtual `/workspace` frame onto the chosen host path (default = the agent's launch `workspace_root`) at every NATS path/cwd boundary. Model-facing shell paths are cwd-relative (`.opengeni/files/...`); durable receipts and `sandbox:/workspace/...` UI links keep the virtual form. `execCommand` returns the SDK banner with combined stdout/stderr and exit code. The "`/workspace` for every run" assumption holds only for provisioned boxes.
- **Targeting a machine at create time.** `CreateSessionRequest.targetSandboxId` (+ optional `workingDir`) selects the machine for a new session; the active-sandbox pointer is seeded at creation so the **first** turn routes there (race-free). `workingDir` without `targetSandboxId` is a **422**, and an invalid/unowned/offline target **422s** rather than silently falling back to the default box. A child spawn with a machine target is an own-box create (omitted `sandbox` no longer inherits a `backend: none` parent); explicit `shared`/`{groupId}` plus a machine target is a **422** (`packages/core/src/domain/sessions.ts`).
- **Never cold-create or kill a user's machine.** An offline self-hosted agent is _not_ a `NotFound`; the lease never provisions a rival box, and the reaper drains a self-hosted box to cold but never provider-stops it. The capability descriptor is `persistable: false` (no disk snapshot) and the box is never idle-reaped.
- **Control surface is NATS, not a provider API.** Exec/fs/git run over a `ControlRpc` request/reply seam addressed to the currently claimed process generation at `agent.<ws>.<id>.connection.<instance>.rpc`, encoded via `@opengeni/agent-proto` (the protobuf wire IDL codegen'd to both Rust and TS so the control plane and agent never drift). `negotiateCapabilities` surfaces online/offline/reconnecting/consent_required/display_unavailable states.
- **Control liveness is isolated from accepted host work.** The Rust supervisor answers `ping`/heartbeats outside execution. Production admission has host-headroom-derived pathology breakers, not an ordinary concurrency/wait limit. Linux uses a manager-owned `supervisor` leaf plus per-operation memory/lifecycle leaves; startup enables memory only, leases CPU only for explicit per-command CPU quota, and leaves I/O/PID untouched. Optional memory and positive integer-millicore CPU policy is revision-fenced and unlimited by default. Every newly admitted exec/Git reads policy, separate memory/CPU capabilities, and exact connection identity from one authoritative snapshot; an in-flight command keeps that immutable admission. Connection/local/ancestor policy may tighten but never loosen it. Once a cgroup manager exists, leaf creation/configuration/pre-exec placement is fail-before-user-code even for unlimited work; there is no changing-member repair loop. A configured policy on an incapable runner fails command execution closed without disabling typed PTY/desktop/browser/computer operations. Admin drop-ins/ancestor policy remain authoritative, and self-update migrates only an exactly proven generated systemd unit. Global kernel OOM remains process-score based: the service requests a negative supervisor score, reports the effective `/proc` value, and a pre-exec hook gives commands the minimal higher victim bias when representable; a supervisor already at the ABI ceiling remains equal. External-daemon work follows that daemon's cgroup/OOM policy. Exec is unbounded by default over replayable op-stream; reconnect detaches, while cancellation or a positive deadline kills the exact process group/Job Object and owned cgroup. Never claim cgroup placement protects against global kernel OOM, ancestor memory bounds guarantee per-command availability, daemon-mediated work remains in the operation leaf, or desired resource policy may be silently ignored.
- **Gated off by default.** The whole feature is behind `OPENGENI_SANDBOX_SELFHOSTED_ENABLED` (default OFF). When off, enrollment routes 404 and the backend is inert — boot is unaffected. Related config: the `OPENGENI_SELFHOSTED_NATS_*`, `OPENGENI_SELFHOSTED_RELAY_*`, and `OPENGENI_SELFHOSTED_RELAY_TOKEN_SECRET` env vars wire the control plane, callout account, and relay tier.
- **Machine UI is opt-in.** Connected-machine React components (machines dashboard, enrollment, status pills, metrics) live on the `@opengeni/react/machines` subpath, so the `@opengeni/react` root import stays a clean sandbox-only default; the root re-exports them deprecated for back-compat (#144).
- Sandbox/enrollment/metrics tables and the session `active_sandbox_id`/`active_epoch` pointer (migration 0024) make sandboxes swappable within a session. The pointer is **establishment-safe**: a swap/seed to a target no turn can establish is rejected before the epoch-fenced CAS with a typed `code`; a persisted-unestablishable pointer is reset to the session home at turn start under the fence with a visible `session.route.reconciled` event. A `null` pointer resolves to the session home when one exists; for `backend:none` it means no compute is attached, while owned Connected Machines remain discoverable and attachable. See `docs/architecture.md` §3.9 and `docs/connected-machines.md`.

Capability Packs compose the ordinary component and compute authorities. A v2 Pack install previews and adopts exact Plugin/Skill/Integration/Facet components, migrates legacy inline `skills` into the shared immutable Skill ledger, and stores an explicit Rig selection; only an `active` top-level Pack owner is runtime-effective, and uninstall removes only that Pack's owner edges. Explicit Rig base images are disabled: every Rig layers on the deployment-owned platform sandbox, and provider-native Rig images are cold-create optimizations whose ids never replace the logical lease image. A v2 Pack that still declares legacy `sandboxImage` is blocked instead of replacing that base. Direct Pack image/Skill runtime remains only for rig-less pre-v2 rows with no frozen manifest digest/snapshot. See `docs/rigs.md` and `docs/packs.md`.

When the `azure` sandbox preparation profile is enabled and ARM/AZURE service-principal variables are allowed into the sandbox, the worker pre-authenticates normal Azure CLI inside the sandbox with `az login --service-principal` before the agent starts. There is no custom `opengeni-azure-login` helper.

Sandbox preparation is controlled by:

- `OPENGENI_SANDBOX_PREPARATION_PROFILES=none`, `azure`, `github`, or comma-separated profile names
- `OPENGENI_SANDBOX_ENV_ALLOWLIST=...` for extra explicit host env vars

Explicit `OPENGENI_GIT_*` settings can set sandbox git author/committer identity. Ambient host `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables only pass through when the `github` preparation profile or env allowlist permits them.

Do not expect model provider credentials to automatically appear in the sandbox unless explicitly allowed.

The API and sandbox file-resource object-storage boundary supports `s3-compatible`, `azure-blob`, `aws-s3`, and `gcs`. Azure Blob-backed Docker/local sandboxes use native Azure Blob manifest mounts. Modal Azure Blob, AWS S3, and GCS file resources use short-lived signed download materialization.

User-message file attachments enter the runtime manifest and eager materialization path only on the exact turn that attached them. Historical attachments remain compact durable `fileId` receipts and must not cause later metadata/object reads, filesystem validation, remounting, or download; retrieve old bytes explicitly through the existing Files MCP plus shell. Historical generated-image receipts likewise never trigger eager sandbox restoration.

## Deployment Work Notes

When working on production deployment, Azure/AWS/GCP deployment, Helm, Terraform, conformance checks, preview variable-sets, observability, or cloud-provider-agnostic infrastructure, treat the source as authoritative: deployment contracts in `packages/deployment`, the Helm chart under `deploy/helm/opengeni`, Terraform roots under `deploy/terraform`, stack wrappers under `deploy/stacks`, and operator docs in `docs/deployment.md`.

Every new SQL migration must declare its reviewed production path on the first lines: `-- deployment-mode: rolling` for online-compatible expand-and-contract work, or `-- deployment-mode: maintenance` for an incompatible one-way cutover. The protected production gate hashes the ordered SQL history and rejects rewrites or unclassified additions.

Migration `0345_tenant_scoped_session_tenancy_fence.sql` is a maintenance-only
writer-protocol cutover. Stop every old API, control worker, and turn worker
before applying it, and never restart a pre-0345 image afterward: the migration
replaces schema-wide session-tenancy table locks with a workspace advisory
protocol and installs database triggers that reject all 17 hot-table mutations
unless the acting backend already holds that workspace fence.

**A migration-time backfill over a FORCE-RLS table must open the owner-only posture window.** `FORCE ROW LEVEL SECURITY` binds the table _owner_, and OpenGeni migrates as a NON-superuser owner without `BYPASSRLS`, with no tenant GUC set. A bare `UPDATE`/`DELETE`/`INSERT ... SELECT`/`DO $$` backfill therefore matches **zero rows and reports success**, and an `IF EXISTS ... RAISE EXCEPTION` preflight certifies a cutover it cannot see. Wrap the statement in `ALTER TABLE "t" NO FORCE ROW LEVEL SECURITY; ... ALTER TABLE "t" FORCE ROW LEVEL SECURITY;` (relaxes only the owner; the app role stays policy-bound; the file is one implicit transaction), set the tenant GUC around it, or use an RLS-immune `ADD COLUMN ... NOT NULL DEFAULT`. `VALIDATE CONSTRAINT`, `SET NOT NULL`, unique-index builds, and RI checks _do_ see every row — which is why a CHECK that evaluates to NULL (and therefore passes) is the trap. `bun run check:migration-rls-backfills` is the CI guard; migration bytes are frozen, so never add to its grandfathered lists. Drive `migrate()` through `acquireOwnerMigratedTestDatabase` to test this boundary. See [`docs/force-rls-migration-backfills.md`](docs/force-rls-migration-backfills.md).

**A test that replays the migration ledger needs an explicit timeout.** Calling `migrate()` - or any `acquire*TestDatabase` helper, which builds the shared template through `ensureTemplateBuilt` -> `migrate()` - rebuilds the whole schema against a fresh database. That cost grows with every migration that lands and is unrelated to the size of the file it lives in. CI packs unit shards by source-file _byte size_, so any unrelated file addition can cluster these tests into one shard, where they run concurrently against a single PostgreSQL container at several times their usual wall time - that is how commit `d13a9849b` turned `main` red without touching a migration. Declare a budget above the 30 s shard default (`180_000` is the convention); `bun run check:migration-test-budgets` (a CI guard, always on) fails otherwise and names each site.

**Every new migration must be registered at all three release-schema contract sites.** `scripts/release-schema-contract.test.ts` pins the ledger in three places a new migration moves: `appendedMigrationPaths` (the forward list, which keeps the migration out of the governed host-export checkpoint input so the pinned aggregate SHA-256 never has to change), a `completeSourceContract.migrations.some(...)` presence probe feeding the pinned `fileCount`, and a `latestMigration` branch in that same assertion, prepended OUTERMOST so the newest migration wins the ternary. The last two pin the _unfiltered_ ledger, so the forward-list entry alone still leaves the contract test red. Do **not** repair any of it by pinning a fresh hash in the `releaseSchemaContractHash` ladder: that aggregate covers the whole filtered ledger, so a hash computed on your branch is stale the moment another migration merges first - the pull request stays green and protected `main` lands red, which is how migrations 0331, 0332, 0333, and 0334 each broke `main` in one day. `bun run check:migration-schema-contract` (a CI guard) fails on any migration this head adds on top of its base that is missing from any of the three, names which ones, and prints the exact edit for each. Advancing the governed checkpoint itself is a deliberate, separate change against current `main`.

Migration ordinals are taken from a shared linear ledger, so two candidates that each add the next free ordinal collide when the first one merges. The migrator orders by full file name and tolerates that, but the release-schema hash ladder, harness stamps, and docs pin the ordinal, so a colliding candidate must move to the next free ordinal as one source revision. Do it mechanically: `bun run migration:renumber <ordinal|basename> --next` (add `--also <path>` for docs/changesets that name the migration by number only; `--dry-run` shows the plan) renames the SQL and its `packages/db/test/migration-<ordinal>-*.test.ts` companions, rewrites every reference, and re-pins `scripts/release-schema-contract.test.ts`; `bun run check:migration-ordinals` (a CI guard) fails with that exact command when a head migration reuses an ordinal already on `main`. Never hand-edit the hash ladder for a rename.

Migration `0117_sandbox_recovery_generations.sql` is a one-way maintenance cutover. Stop every old API, control-worker, and turn-worker writer before activation; activation rejects a live `opengeni_app` session and rolls its transaction back cleanly. Application/image rollback to an old writer is allowed only before migration activation. After activation, no old writer may restart; move forward with the protocol-v2 application because there is no mixed-version or down-migration path.

Canonical organization-tenancy authority activation is the same one-way shape, per subsystem. Before a subsystem's activation, tenancy columns and authority/grant rows are additive facts rather than the access decision, so an application/image rollback stays an ordinary deployment decision and the legacy workspace-owned lane remains byte-identical. After it, only forward recovery is permitted and a pre-activation image must never restart - `0264_connection_authority_runtime_activation.sql` and `0275_scheduled_connection_authority.sql` have already crossed that boundary for the Connection and scheduled-Connection-authority surfaces. `OPENGENI_ORGANIZATION_TENANCY_CANONICAL_ACTIVATION_ENABLED` (default off) is the named pre-activation opt-out an operator uses to decline or defer activation; it is not a kill switch. The session-tenancy activation command enforces it, and API/worker startup fails closed with it disabled after any durable activation exists. Setting it back to false after activation restores nothing. New activations additionally require the settled 0340 membership/session/resource/connection receipt set, bind those six exact receipt ids, and recompute the supplied inventory/parity digests under the database source-table fence. The operator takes those source locks before the owner-only `session-tenancy-canonical-boundary:v1` advisory fence; future greenfield provisioning must write its complete graph before taking that same fence and checking the committed witness, or the reversed global/source order deadlocks. Migration 0340 also makes the connection `legacy_user` lane finite: only exact subject + active same-organization membership evidence may upgrade it; after activation no new legacy authority may be minted, surviving rows are runtime-invisible, and pre-snapshot workspace references without a connection id are refused. Do not weaken the drained-writer guard, infer ownership to clear a backfill precondition, or hand-edit tenancy authority/grant tables to undo an activation. See [`docs/organization-tenancy.md`](docs/organization-tenancy.md) for the boundary and preconditions and [`docs/deployment.md`](docs/deployment.md) for the operator procedure.
